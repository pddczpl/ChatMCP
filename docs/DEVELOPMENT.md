## Dynamic task tool schemas

The Hub offers each task either all 99 LocalTools plus the four internal routers (103 schemas, about 15.4k tokens) or the at most 48 LocalTools relevant to the prompt plus the routers (3.1k tokens for a prompt that names no task, 3.9k for one that only asks for a change, 7.7k at most for the corpus below). The foreground chat (the primary runner) follows the context window of the model of the task it starts: an unknown window, or one below 65,536 tokens, gets the selection; 65,536 or more keeps the full list. Background chats always use the selection. `CHATMCP_TOOL_SELECTION=auto` or `=full` overrides the choice either way, and a runner built without a mode (as the tests do) is still `full`. Tools not directly advertised remain registered in the original catalog and reachable via internal `mcp_catalog`, `mcp_describe`, `mcp_call` behind PermissionGate. A run selects on the conversation, not on its first message: the prompt of the run that starts (a continuation included) is matched by words, in English and Vietnamese, to groups of tools, and the up to 20 prompts before it, newest first (a message queued while an earlier run was going counts as one), then add the tools there is room for under the cap. So a follow-up that asks for something new is offered what that needs ("Now update the version in package.json and commit it." after "Explain what calc.js does." gets `edit_file` and `git_commit`), a follow-up that names no task ("yes, go ahead") keeps the tools the conversation has been using, one that names only part of the work (the prompts the Hub writes for an auto-resume or a repair name the edit and test tools) keeps the rest, and no message is offered less than it would be as the first message of a conversation. A conversation can therefore approach the cap: in three five-message coding conversations the fourth and fifth messages were offered 38-45 tools (6.9-7.8k tokens, against 4.0-5.1k when each message is matched alone), which leaves 2.0-2.9k tokens of history on a 16,384-token window (4.7-5.9k when each is matched alone). A run keeps its tool list from start to finish, because its context budget is planned on it: a message queued while it runs is delivered to it, the instructions tell the model that the list is fixed and that `mcp_describe` and `mcp_call` reach the rest, and the message counts when the next run selects. The `tool_selection` event records the prompt of the run and how many earlier prompts were read. The words are the original trigger words (fix, test, browser, commit ...), the general change verbs (update, add, remove, replace, convert, bump, cập nhật, thêm, xóa, đổi ...), the words of a failure report (crashes, TypeError, lỗi ...), plurals (tests, commits) and phrases such as "who calls", "mobile", "CI" or "PR". A change verb offers the four tools that change a file (about 0.8k tokens), not the whole edit group. What the later words add comes after what the original triggers offered, so the cap of 48 can only cut the additions and a prompt that matched before is offered at least what it was. A word the lists do not know still reaches every tool through `mcp_describe` and `mcp_call`, one round trip dearer. `tests/fixtures/tool-selector-corpus.json` lists 87 prompts with the tools a correct solution calls, and `tests/verify-tool-selector.mjs` measures them: every one of those tools is offered directly (the original trigger words alone offered 58% of them, and 33% of those that no prompt gets by default), the median schema cost is 4.7k tokens and no prompt costs more than 7.7k. Measured through the real runner and catalog for a coding prompt against an unconfigured window: fixed overhead 15.4k -> 8.2k tokens, history 10.3k -> 15.3k tokens.

**Skills follow the conversation too, and what the Hub writes does not choose.** Skills are chosen the way the tool schemas are: the prompt of the run that is starting chooses first, as it would as the first message of a conversation, and the up to 20 earlier prompts of the conversation, newest first (the person's, and the ones the Hub writes itself to resume or repair a run, which are read as words like any other), add the skills there is room for, under the same limit of 4 skills and 8,000 characters in all (`selectConversationSkills` in `lib/agent.mjs`; one pass per prompt and never the prompts joined, so four skills named earlier cannot push out the one the newest message names; `verify-skill-delivery`). What is chosen reaches the model as the index described under Skills on demand. Selection reads three things and nothing else: the prompt of the run, the earlier prompts of the task, and `carriedPrompts` (the person's own requests that a task carries from before it began in another channel); the instructions, the project guidance, the skill index, the completion notice of a background agent and a hook's feedback are not among them, so none of them can choose a tool or a skill or count as something the person asked (`verify-subagent-notices`, `verify-hooks-lifecycle`, `verify-e2e-prompt-budgets`). The text a caller wraps around a goal does not choose either: a coding worker is chosen for by its goal alone (`selectionPrompt` in `lib/coding-orchestrator.mjs`), and a background agent that carries a conversation from another channel or the results of earlier workflow phases is chosen for by its goal and, for the first, the person's own requests (`lib/concurrent-api-agent.mjs`; `verify-tool-selector`, `verify-skill-delivery`), not by the Hub's sentences in the handoff or by another agent's answer.

An unknown context window is planned as 32,768 tokens and shown as a warning on the task (`conservative_fallback`). The request may still ask for the full default output (16,384 tokens; v3.9.0 sent 18% of the estimate, 5,898, which ends a reasoning answer as incomplete) while the history is planned against a quarter of the estimate. A window is 4,096..2,000,000 tokens everywhere it can be set (`lib/context-window.mjs`): smaller is refused with `invalid_context_window`, larger is clamped. A window the owner did not set is the model catalog's when the catalog is sure of the model (an `exact` or `normalized` answer, never an `alias`; `lib/model-facts.mjs`): `GatewayProvider.effectiveContextWindow()` is the owner's window, else the `capacity` of the catalog (`modelCapacity`, what the model allows: the window, or, when the model takes in less than its window, the largest capacity whose planned prompt is not longer than `maxInput`: at most `maxInput` plus the 16,384 tokens the agent asks to write, worked out with the same two reserve formulas as the budget of a run in `lib/context-reserve.mjs`; clamped to 4,096..2,000,000; then stopped at the first point where the price of that provider's row of that model rises with the length of the prompt, the lowest `aboveTokens` of a tier that costs more than the base price, but never below `PRICE_CAP_FLOOR_TOKENS`, 128,000, and never above `modelCapacity`: `priceCap` says which rise stopped it), else none. `state().contextWindowTokens` stays what the owner saved; `effectiveContextWindowTokens` is what the Hub plans on and `contextWindowSource` says where it comes from (`configured`, `catalog`, `fallback`); the run records the budget as `trusted_model_metadata`. The tool selection (`followProviderWindow`: 65,536 and more keeps the full list), the adapter's trimming of history and the plan of every run read the effective window. The request asks for the model's own output limit when the catalog has one (`outputCap`, clamped to 1,024..16,384). A larger window starts compaction later: the Anthropic preset used to plan on 200,000 tokens and now plans on the 1,000,000 of Claude Sonnet 5.5, so a long run can send more tokens per step until the owner types a smaller window; no preset carries a window of its own any more (DeepSeek's 128,000 went with `deepseek-chat`, retired on 2026-07-24: its default model is now `deepseek-flash`, which the catalog knows at 1,000,000).
Selection does not remove tool permissions and must be benchmarked before
claiming lower total request consumption.
Parallel coding workers use the bounded 48-schema `auto` selection by default; the ordinary single-agent flow keeps its existing full-tool default unless configured.
When launching a parallel coding DAG, DatGold also enforces one aggregate
HTTP model-request allowance shared by its workers:
`CHATMCP_MAX_WORKER_HTTP_REQUESTS=120` (0 to disable). It counts retries and
Gemini repair/fallback attempts, and never bypasses an individual worker's
task-scoped request cap. The aggregate is reset for each newly authorized
coding DAG; no separate Windows Sandbox rules are modified.

## Prompt budgets: project instructions and skills on demand

Two kinds of third-party text reach the prompt of a task on purpose. Both are bounded, labelled as untrusted and recorded, and neither can change what the permission gate decides: the gate reads the tool call, never the model's reasons.

**Project instructions** (`lib/project-instructions.mjs`). When a run starts (a continuation reads the files again) the runner reads `AGENTS.md`, `CLAUDE.md` and `.claude/CLAUDE.md` from the root of the workspace, in that order, and puts one block into the agent's *instructions*, between the Hub's own rules and the tool list. In the instructions and not in the conversation, because there the context budget counts it as fixed overhead (`fixedOverheadTokens`), history compaction cannot drop it, and the bytes up to its end do not depend on the tool selection, so a prefix that a provider has cached stays a hit (`tests/verify-project-instructions.mjs` compares the prefixes of runs that select different tools). The whole block, headers, fence and truncation markers included, is at most **8,192 bytes**, and less where the room of the run is small. What the instructions say is sent again with every request of the run and takes room from its history, and a run whose known window leaves its history under 1,000 tokens is refused (`context_limit`); a full block did that to runs that worked on a window of 10,000 or 12,288 tokens (history 1,356 -> 0 and 3,072 -> 916 tokens, measured with the real budget function on the instructions of a real run). So the guidance is a share of the history budget the run is planned on (`promptAllowance` in `lib/prompt-allowance.mjs`): **10%** of it for the block and **5%** for the skill index with the definition of `skill_load` (below), 15% together, and together at most half of what is left above that 1,000-token floor, so that even if JSON's escaping doubled what they cost the history would stay above it. Both are sized last, in the preparation of the run, on the instructions and the tools the run really has: the text for the spawn tools, the check discovery, the plan and the token rules all follow the guidance, a busy project makes them large, and a reserve for them would be a guess; the one sentence of the rules that changes when there is a block (it says that the files are in it) is charged to the block's share. The same rule serves every window. A large one reaches the 8,192 and 4,096 bytes; an unknown one is planned as 32,768 tokens, the number the run plans its history on, and gets a share of that plan (it used to get the maximum); a small one gets less. Measured by `tests/verify-project-instructions.mjs` with 22 tools of about 500 characters of description and a project with the spawn tools, eight check suggestions and a plan: a window of 13,000 tokens gets no block (the run has 1,110 tokens of history, just over the floor), 16,384 get 1,280 bytes (history 3,648 -> 3,289 tokens), 24,576 get 3,584, 65,536 and more get the whole 8,192, and an unknown window gets 5,632; with four tools instead of 22 a window of 16,384 tokens gets 2,560; in a real Hub with the auto tool selection and a project with ten checks the same window gets 2,048 (`verify-e2e-prompt-budgets`). The cap is a multiple of 256 bytes, so the few tokens a tool more or less moves the budget by do not move the cut of the block, and with it the bytes up to its end that a provider caches; a large change of the tool list does move it. What is cut stays one `read_file` away: the marker names the file and the bytes cut and says how to read the rest, a file left out for lack of room is named with the call that reads it, and with no block at all the rules tell the model to read the files itself. The `instructions_loaded` event says when and why the limit was lowered (a small window or an unknown one), in numbers, and the record keeps them (`budget`: reason, source, window, planned history, tokens, percent). The first file fills the room; a file that does not fit is cut on a character boundary (at the end of a line when one is near) with a marker that names the file and the number of bytes cut, and a file after it that finds no room is named as not loaded. A file with the same text as an earlier one (a copy, or `CLAUDE.md` as a link to `AGENTS.md`) is loaded once. Only these three names at the workspace root are read. A nested `AGENTS.md` is not: the task root is the working directory the agent starts in, the cap leaves room for a handful of files and not for a walk through a monorepo, and which subfolder matters is known only when a file in it is read, not when the task starts (the agent reads a nested file with `read_file` like any other). A file of a parent folder is not either: it is outside the workspace. A file is opened only if its real path (links and junctions resolved) is inside the workspace and is not a protected file, it is a regular file of at most 256 KiB (a larger one, a 2 GiB file included, is refused from its size and never opened, and the read asks for one byte more than the limit, so a file that grew in the meantime is refused too), and it is UTF-8 (a BOM is dropped) or UTF-16LE with a BOM; binary files, text that is not UTF-8 and UTF-16BE are refused with a reason, not guessed. Line endings become LF, so the same project gives the same bytes on every checkout. Invisible and control characters (tag characters, zero-width and bidi controls, escape codes), the carrier of hidden instructions, are removed and counted, and what looks like a credential is masked by the runner's own redactor, the one every tool result goes through, in that order so that a hidden character inside a key cannot hide it. The line that ends the block carries an id made from the text, so a file cannot contain the line that closes its own block. Each run records an `instructions_loaded` event and `task.projectInstructions` (per file: path, status, reason, sizes, sha256 of the file on disk and of what was loaded; for the block its size and sha256; never a text). The owner's switch has three sources, strongest first: `CHATMCP_PROJECT_INSTRUCTIONS` in the environment of the Hub (`off`, `0`, `false`, `no` and `disabled` turn the loading off, `on`, `1`, `true`, `yes` and `enabled` keep it on, anything else decides nothing; read once, when the Hub starts), the choice the owner saved in Settings (Project → Project instructions; `{version, enabled}` in `project-instructions.json` of the Hub's data folder, written atomically), and the default, on. `/api/state` has `projectInstructions` (`enabled`, `source` which is `env`, `config` or `default`, `saved` which is the saved choice whatever decided, the variable, the byte cap and the file names). `POST /api/agent/project-instructions {enabled}` sits behind the same layers as the other config routes (bearer, Origin, page marker, CSRF; it is in `POST_ROUTES`, so `verify-hub-auth` enumerates it) and saves the choice: a value that is not `true` or `false` is refused with 400, and so is any change while the variable decides (409 `project_instructions_env`: a choice that cannot take effect must not look as if it had). It is not refused while a task runs, like the transport of `/api/agent/mode`: it applies to the NEXT run, because `AgentRunner` is given the Hub's `ProjectInstructionsStore` and asks it once at the start of every run (a fixed `{enabled}` still works for a caller that wants one). So the foreground runner, a pooled chat that runs in its own worktree (kept and reused for the next message) and a coding worker, whichever already exist when the choice changes, follow it from their next run, and a run that is going keeps the block it was given. The store is loaded right after the manager, before any runner exists and before the Hub says it is initialised, so the first task after a restart already follows the choice; a file that cannot be read costs the owner the saved choice and nothing else (the default applies, one line in the Hub log says so). A task that ran with the loading off says so. Only `AgentRunner`, the Model API channel, loads these files; the ChatGPT Web runner does not. The page shows the switch (Settings → Project) and, under each finished turn, a line with the files that run loaded (name, size, how much was cut, or "off") and the skills the model read on demand with `skill_load`: a record of what the Hub did, never drawn like the evidence strip, because loaded is not followed (`ui/src/lib/project-instructions.ts`, `ui/tests/project-instructions*.test.mjs`).

**Skills on demand** (`lib/skill-index.mjs`). The conversation used to carry the whole text of up to four selected skills (8,000 characters) with every model request of the run. It now carries an index of at most **4,096 bytes** (less where the room of the run is small, see below): for each selected skill its name, id and licence and, when the text is at most 1 KiB (a tool round trip costs more than that), the text itself; for a bigger skill one line with what it is for, its size and the call that reads it. The index is still a user-role message that begins with `UNTRUSTED SKILL REFERENCES` and never goes into the instructions. The model reads a skill with `skill_load {id}`, a host function (like `spawn_agent`) that is offered last in the tool list whenever the index sends the model to it (a selected skill is on demand or is not listed) and the share of the room can pay for it, in `full` and in `auto` tool selection alike and to every runner that starts a task, workers and subagents included. What comes back is the text, once per load, as the tool result: at most 16 KiB (cut like the project files), cleaned and masked like them, labelled as untrusted data, and never copied into the activity log. The index and the tool are paid out of one share, 5% of the planned history, because the definition of `skill_load` is 526 bytes of JSON in every request (it was 802 before it was shortened, which decided whether a model with 16,384 tokens could be offered a bulky skill at all) and is not part of any reserve: `fitSkillIndex` builds the index as it is when every skill in it is carried whole (no tool); else the index that fits in what the tool leaves of the share, down to only the ids of the skills with the way to read them (`skill_load` offered); else, when the tool cannot be paid, only the skills that are carried whole (no tool); else nothing. A skill the model is told nothing about is dropped, and `skills_activated` says how many and why (`skillIndex`: `bytes`, `maxBytes`, `dropped`, `tool`, `budget`). With 130 KB of project files and four skills, three of them big (`verify-skill-on-demand`): at 16,384 tokens and 22 tools the index carries the small skill (263 bytes of 768), the three others are dropped and there is no tool; at 16,384 tokens and four tools the index is 632 bytes, `skill_load` is offered and nothing is dropped; at 200,000 tokens or an unknown window all four are in the index (885 bytes) with the tool; at 12,500 tokens there is no index at all and the run completes. A repeat load says where the text already is unless `force: true` is given; an unknown or malformed id answers with the list of skills that can be read. Recorded: `skills_activated` (what the index carried and what is on demand), `skill_loaded` (the hash of the skill as installed, of what was loaded and of what the model was given, the sizes, whether it was forced) and, in the transcript, the delivered text. How big a skill is no longer decides whether it is selected, so the 8,000-character budget is gone from the run (the limit of four skills stays). What a model that never calls `skill_load` gets: every small skill, as before, because the nine skills the Hub ships are all small (one small skill: 262 bytes of conversation per request before, 263 now); not the text of a big one, which costs a line instead of its text on every request (a small and a 6 KB skill: 6,652 bytes before, 570 now; a skill of 100 KB: 12,768 before, 476 now) and which the index tells the model it has to ask for. `skill_load` returns text the owner installed and decides nothing, so it does not go through the permission gate or the hooks (like `spawn_agent`; `docs/THREAT-MODEL.md` Surface 6).

Tests: `verify-project-instructions` (the loader on real files; the allowance, with anchors worked out by hand and properties over every history from 0 to 60,000 tokens; then the real runner with a busy project: the cap of every window is `promptAllowance` of the policy the same run has with the guidance switched off, and the guidance never takes the history under the floor; exactly once per request with a mutation check, the stable prefix, the records, the switch, a hostile `AGENTS.md` through the real manager and gate), `verify-skill-on-demand` (the index and the tool; the ladder; then the real runner and plugin manager with 130 KB of project files and four skills on windows of 12,500, 16,384 and 200,000 tokens and an unknown one, with the budget recomputed from what the provider received; a pooled worker, a hostile skill through the real gate, redaction, the measurement above), `verify-skill-delivery` (installed skills still reach the model: whole when small, once after the call when big), `verify-e2e-prompt-budgets` (a real Hub process and a scripted model server: what is sent over HTTP, request by request, with a model of 200,000 tokens and one of 16,384), `verify-project-instructions-setting` (the precedence, the store, the real runner and a pooled chat and a coding worker whose runners exist before the choice changes) and `verify-e2e-project-instructions-switch` (the route and its layers on a real Hub, the NEXT request of the model server with and without the block, a change while an approval is pending, a restart, the variable, a damaged file); the page has `ui/tests/project-instructions.test.mjs` (the words and the rules), `ui/tests/project-instructions-components.test.mjs` (the real components rendered, and never in the colours of the evidence strip) and `ui/e2e/project-instructions.spec.mjs` (Playwright against a real Hub).

## Request and token telemetry (no DatGold quota)

DatGold **does not impose HTTP request, token or spending caps**.
Provider billing and quota are controlled by the user/provider. No
`CHATMCP_MAX_HTTP_REQUESTS`, `CHATMCP_MAX_INPUT_TOKENS`,
`CHATMCP_MAX_OUTPUT_TOKENS` or `CHATMCP_MAX_WORKER_HTTP_REQUESTS`
limits are enforced. The AgentRunner counts real model HTTP sends including
retry/fallback/repair requests. `task.usage.httpRequests` persists
through task resume. Worker orchestration sums HTTP sends for reporting,
not to block tasks. Provider-reported tokens may exclude timed-out or
unbilled requests and should not be treated as exact charges.

## Background agents: results and completion notices (P1-F)

An agent that starts others (`spawn_agent`, `spawn_workflow`) can read what they produced and is told when one stops, without polling. The logic is in two modules that do no I/O, `lib/agent-results.mjs` and `lib/subagent-notices.mjs`; `AgentRunner` and `ConcurrentApiAgent` only hold the hooks. The threat model is Surface 5 of [THREAT-MODEL.md](THREAT-MODEL.md); what the person sees is in [USER-GUIDE.md](USER-GUIDE.md).

**`agent_results`** is read-only. It answers from the pool's records of the calling task's own children (`ConcurrentApiAgent#listSubagents`, reached through `manager.listSubagents`, which the pool sets on its own manager and on every child's), and it is offered where the spawn tools are and to a task that already has agents (a full tree still has to read them). Arguments: `ids` (optional; any id that is not a child of the caller answers `found: false` and nothing else) and `offset` (with exactly one id: reads on in a cut final message). The answer is JSON. For each agent: `id`, `goal` (the parent's own words: the prompt that the child's runner stores also carries the Hub's predecessor handoff), `role`, `workflow`, `status`, `createdAt`, `startedAt`, `finishedAt`, `durationMs`, `claim` and `hubRecord`.

- `claim` is the child's final message: model output, `verifiedByHub: false`, redacted before it is cut, one page of at most 8,000 characters, with a marker in the text and `claim.next.offset` when it is cut. The Hub's own sentences are not part of it: the "[Verification notice]" the runner adds when the Hub could not back the run, and the "[Hook notice]" it adds when a Stop hook still objected after its eight blocks. The runner records where the model's words end when it makes the final text (`finalParts` on the task, `lib/final-text.mjs`) and the claim is exactly those words; a task saved before that record is cut by the older rule, which knows only the verification sentence.
- `hubRecord` is what the Hub recorded: steps, tool calls, the receipts it made itself (`shaCheckedEdits`, `shaCheckedReads`, `passingChecks`, `diffReviews`: tool activity it saw, not proof the work is right), unverified operations, the error code and message, the branch, and the Hub's two sentences from the end of the final message when there are any (`verificationNotice`, `hookNotice`; bounded, and not in the compact form). `verificationOutcome.ready` is never shown: it is also true when nothing needed checking.
- Bounds, guaranteed and not a target: 16 agents per call (the newest, oldest first, `omitted` counts the rest) and 24,000 characters in all; the answer is rebuilt with less text, then less detail, then fewer agents until it fits. There is no clock in it, so a parent that polls an unchanged child gets the same bytes and the no-progress detector stops it (a recovery hint after 4 repeats, a stop after 10).

**Notices.** The pool sees a child stop (the END event of its runner, plus the endings no runner reports: blocked by a failed dependency, cancelled while queued, failed before it started) and calls `AgentRunner#recordSubagentFinished` on the runner that holds the parent task. That keeps one entry per child in `task.subagentNotices` (at most 64, in `task.json`, validated again by `load()`; `recorded` then `delivered`) and adds the event `subagent_finished`. The model is told by `#tellAboutAgents`: one host message of kind `completion_notice`, added only where no model turn is open, so it follows every result of the turn before it and is never between two:

| the parent is | what happens |
|---|---|
| running, or waiting for an approval | the entry is recorded at once; at the next boundary (the top of the loop, behind `HistoryLedger.endBatch`) the message is added, in front of a message the person queued; event `subagent_notice` |
| writing its final answer when the child stops | the run goes on instead of finishing (the ledger drops what waits when a run ends), the message is added and the model answers again; not when a step limit, the deadline, a stop or the size of the context would end the run at the top of the loop (the answer stands, the entry stays `recorded`), and at most 64 times |
| finished | the entry is only recorded (`subagentNotices[].notice` in its state, the event, nothing started, no request); the next run adds the message before its prompt, once |
| restarted | `load()` restores the entries; nothing is sent or recorded; a delivered entry is never told again, an unread one is told by the next run |

The message is the Hub's: ids, role, how each agent stopped (the word for `completed` is "sent its final answer", which is all it means here), when, the goal the parent wrote (quoted on one line) and a pointer to `agent_results`; nothing an agent wrote. It is never put in `task.prompts`, `task.dialogue` or `task.carriedPrompts`, which are what tool and skill selection and the conversation read, so it selects nothing and does not count as something the person asked.

Two behaviours a reader would not guess. A notice for a conversation that is not running is recorded as an ordinary event, so it updates the conversation's `updatedAt` and the conversation moves to the top of the list when its agents stop. And the notice is a plain user-role item in the history: its kind (`completion_notice`) exists only in the ledger's `onAppend` metadata, so code that wants what the person asked must read `task.prompts`, never the last user item of the ledger (the Hub's other host messages, such as a recovery hint or a resume checkpoint, are the same).

Not covered. The coding orchestrator's workers (`lib/coding-orchestrator.mjs` builds each a plain `HubManager`, which has no `listSubagents` and no spawn function) and the dynamic delegates (`lib/dynamic-delegates.mjs`, `lib/studio-delegates.mjs`: the Hub itself collects their results) have no parent model to tell. A child's own task files keep its final message as it wrote it (RR-6, RR-14). The `agent_results` call is not hooked, like the spawn calls (RR-11); `SubagentStop` is a separate matter. With `CHATMCP_DIRECT_TOOL_LIMIT=124` the three host functions (`spawn_agent`, `spawn_workflow`, `agent_results`) take the advertised functions past 128, as the two spawn tools already did.

## Trạng thái Windows Sandbox (Phase 1 experimental)

**Chưa có bằng chứng cách ly Windows Sandbox guest thật.** Việc build .NET GuestSupervisor
và chạy lệnh synthetic trực tiếp trên Windows host chỉ chứng minh hành vi host-fixture
(timeout, Job Object, parser). Phần này tuyệt đối không được tính là kiểm thử host/guest
isolation, network denial, supervisor identity hay receipt authenticity.

CI Windows installer phải build GuestSupervisor và chạy
`CHATMCP_REQUIRE_HOST_SUPERVISOR=1 node CHATMCP-HUB/tests/windows-sandbox/smoke.mjs`.
Trên Linux/Windows thiếu .NET, bộ source test nêu rõ **BLOCKED** đối với fixture chưa chạy;
bộ kiểm thử guest thật do máy Windows hỗ trợ thực hiện tách khỏi CI thông thường. Backend sản phẩm và các mô-đun snapshot/check grants/retry/subagents đã có mã nhưng cố ý báo unavailable cho đến khi trusted publication được nghiệm thu.

`receipt.json` và `receipt.sha256` chỉ kiểm tra dữ liệu nhất quán; guest có thể tạo
lại cả hai file và đọc nonce, nên đây KHÔNG phải bằng chứng về danh tính supervisor.
Thư mục export có thể ghi vẫn là bề mặt tấn công host, chưa có quota OS/ACL pinning.
Windows Feature đang chờ khởi động lại không chặn các bài test này.

## Giới hạn công cụ trực tiếp

Từ nhánh nâng cấp LocalTools, `directToolsFor` quảng bá tối đa **99 LocalTools + 4 router** (103 schemas) ở cấu hình mặc định; không còn bài kiểm thử áp đặt dưới 50. Có thể đặt biến môi trường `CHATMCP_DIRECT_TOOL_LIMIT=48` (compact) hoặc `=95` (full); giá trị hợp lệ 0-124, vượt 124 được chặn để giữ tổng advertised functions không quá 128. `0` chỉ giữ các router nội bộ. Các tool không quảng bá trực tiếp vẫn ở catalog và gọi được qua `mcp_call`. Hãy chọn giới hạn thấp hơn nếu provider có tool-limit hoặc prompt-context nhỏ; thay đổi yêu cầu khởi động lại Hub. Đây là giới hạn gửi schemas **không** phải giới hạn quyền PermissionGate hoặc tổng số tool đã đăng ký.

## Chạy kiểm thử

```powershell
cd CHATMCP-HUB
npm test                                         # mọi bộ Node, mỗi bộ một tiến trình riêng
node tests/run-all.mjs --list                    # liệt kê
node tests/run-all.mjs --filter e2e --verbose    # lọc theo tên, in toàn bộ đầu ra
node tests/run-all.mjs --json test-results/summary.json
node tests/run-all.mjs --no-skip all             # một bộ bị SKIP bị tính là FAIL (dùng cho CI)
node tests/run-all.mjs --retry-failed-once       # bộ FAIL/TIMEOUT được chạy lại một lần; qua ở lần hai = FLAKY, không phải PASS
node tests/run-all.mjs --fail-on-flaky           # một bộ FLAKY làm cả lượt chạy thất bại (dùng khi cần sạch hoàn toàn)
npm run test:ui                                  # bộ giao diện Python/Playwright (tùy chọn)
```

Hiện có **167 bộ Node** (`tests/verify-*.mjs`) và **5 bộ giao diện** (`tests/verify-*.py`, cần Python + Playwright). Hai con số này được bộ `verify-docs` đối chiếu với thư mục `tests/`, nên không thể lỗi thời mà không bị phát hiện.

Runner in một dòng cho mỗi bộ (`PASS`/`FAIL`/`TIMEOUT`/`SKIP`, thời gian, mã thoát thật) và thoát khác 0 nếu có bộ nào fail hoặc quá hạn (mặc định 180 giây/bộ, đổi bằng `--timeout`). Bộ kiểm thử in một dòng `CHATMCP_TEST_SKIP: <lý do>` rồi thoát 0 để được báo là **SKIP — không bao giờ được tính là PASS**. `--no-skip all` (hoặc `--no-skip tên1,tên2`) biến SKIP thành FAIL. Workflow hiện tại cài Python 3.11 và các gói ghim trong `tests/requirements-e2e.txt`, rồi chạy **`--no-skip all`** trên cả Windows và Linux, Node 22 và 24. Một bộ bắt buộc bị bỏ qua vì thiếu môi trường vì thế làm CI thất bại. Một phần không thể kiểm chứng trong bản này được in `BLOCKED: <gì> - <vì sao>`.

**Bộ chập chờn (`FLAKY`).** Với `--retry-failed-once`, bộ FAIL hoặc TIMEOUT được chạy lại đúng một lần. Qua ở lần hai thì nhãn là **`FLAKY` — không bao giờ là PASS**: được đếm riêng (`summary.flaky`), kèm cả hai lần chạy và đầu ra của lần hỏng trong JSON, một dòng `::warning` trên GitHub Actions. Hỏng cả hai lần vẫn là FAIL; bỏ qua (SKIP) ở lần hai cũng là FAIL. Một lần FLAKY không làm lượt chạy đỏ; `scripts/ci-flaky-gate.mjs` (job `flaky-gate` trên `main`) làm nó đỏ khi lần chạy này và hai lần chạy trước trên `main` đều có bộ FLAKY. Xem [CI-HEALTH.md](CI-HEALTH.md).

**Máy chủ LSP thật trong CI.** `tests/verify-lsp-tier.mjs` luôn chạy với máy chủ LSP giả; `typescript-language-server` và `pyright` thật chỉ chạy khi tìm thấy (thư mục `node_modules` trong `CHATMCP_LSP_NODE_MODULES`, hoặc bản cài npm toàn cục) và nếu không thì chỉ in một dòng `skip`. Job Windows installer của CI dựng runtime đã khóa bằng `scripts/intelligence-runtime/stage.mjs` (đúng các tệp installer đóng gói) rồi chạy `CHATMCP_REQUIRE_REAL_LSP=1 CHATMCP_LSP_NODE_MODULES=<runtime>/runtimes/lsp/node_modules node CHATMCP-HUB/tests/verify-lsp-tier.mjs`: với biến này, thiếu một máy chủ thật là **lỗi** (và chỉ thư mục đó được tìm, bản cài toàn cục không thay thế được). Bộ `verify-lsp-real-gate` chạy chính tệp đó trong từng tình huống và đọc mã thoát. Bước CI này chưa từng chạy trên GitHub trong bản này; đã chạy cục bộ trên Windows 11 / Node 24 với typescript 5.9.3, typescript-language-server 4.3.4, pyright 1.1.407.

Tổng thời gian cả bộ Node: khoảng 3 phút (Linux, 180 s đã đo) đến 4 phút (Windows, 243 s đã đo); bộ lâu nhất là `verify-e2e-recovery` (~57 s, vì phải giết và khởi động lại Hub nhiều lần).

### React/Vite E2E và Windows WebView2

Chạy từ thư mục gốc của repository:

```powershell
cd CHATMCP-HUB/ui
npm ci --no-audit --no-fund
npx playwright install chromium
npm run test:unit
npm run test:e2e
# Chỉ dùng khi đã build cùng mã nguồn cần kiểm tra:

# Windows: cần .NET SDK 10 và WebView2 Runtime, dùng build React vừa tạo:
```

`test:e2e` chạy TypeScript + Vite build trước khi mở Chromium headless. Local Hub thật phục vụ `web/dist`; không chặn hoặc giả response của Hub, không dùng trang legacy. Mỗi ca tạo kho Git, state Hub và model server loopback riêng trong thư mục tạm; môi trường tiến trình Hub được lọc credential và cấu hình Git cá nhân. File, command, permission gate và Git đều chạy thật. Bộ test dọn tiến trình và dữ liệu tạm sau khi chạy.

Các luồng được kiểm tra từ React: onboarding, chọn workspace, lưu và kiểm tra model, tạo hội thoại trống không gọi model, gửi prompt, tool receipts, preview/rủi ro và Approve/Deny, sửa file và chạy test, Git diff, Files/Activity/Skills, kế hoạch trống và checklist có bằng chứng, Stop/Resume cùng ID, lịch sử sau khi khởi động lại Hub ở trạng thái đã dừng, đổi quyền trong Settings, và test thất bại không trở thành thông báo thành công. Terminal được tạo qua API được bảo vệ của Hub để xác minh tab đọc output/mã thoát của phiên thật. Bộ browser xác nhận kết nối `/api/tasks/events`; token routing có unit test. Streaming token từ provider thật vẫn cần kiểm chứng riêng.

Console errors, runtime exceptions, HTTP lỗi và API error envelopes làm E2E thất bại. Trạng thái task bị hủy theo yêu cầu vẫn là dữ liệu hợp lệ. Một ca dùng API key giả trong fixture để kiểm tra input được xóa sau lưu/đổi provider/đổi origin, và request cấu hình mới không mang key cũ; không dùng credential cá nhân hay gọi model trả phí. Reporter bắt buộc làm cả run thất bại nếu có `test.skip`; `ui/tests/e2e-gate.test.mjs` xác minh mã thoát thật của trường hợp đó. Cổng đọc thân phản hồi API không chờ vô hạn (`ui/e2e/response-body.mjs`): `page.reload()` có thể cắt một phản hồi giữa header và thân, khi đó Chromium không trả thân cũng không báo lỗi, nên phản hồi của tài liệu cũ được bỏ sau 1 giây (ghi vào `browser-warnings.json`, không tính là lỗi), còn thân không tới trong 10 giây trên một trang đứng yên làm test thất bại kèm URL; hai ca này nằm trong `ui/tests/e2e-gate.test.mjs` (lỗi "Tearing down exceeded the test timeout" của job Windows trước đây là do chờ vô hạn ở đây, không phải do Hub, xem `docs/CI-HEALTH.md`). Kết quả JSON, Hub logs và ảnh/trace khi thất bại nằm trong `ui/test-results/` và được CI lưu làm artifact.

CI chạy React unit + Chromium E2E trên Windows và Linux. Job Windows installer chạy smoke WinForms/WebView2 sau build và thất bại nếu thiếu prerequisite; tham số `--allow-unavailable` chỉ dành cho khảo sát local và không dùng trong CI. Native smoke này kiểm tra tải/điều hướng, không thay thế toàn bộ luồng agent của Chromium. Restart React kiểm tra phiên đã dừng; crash giữa thao tác và chống phát lại mutation thuộc các regression Hub như `verify-e2e-recovery`.

Mô hình ở các ca này là máy chủ **theo kịch bản**, không phải model thật. Kết quả không xác nhận chất lượng model trả phí, OS isolation, hay fresh install/upgrade/uninstall trên Windows sạch. Xem thêm [hướng dẫn E2E React](../CHATMCP-HUB/ui/e2e/README.md).

## Bộ E2E: thật ở đâu, giả ở đâu

`tests/e2e/` là một khung nhỏ dùng chung:

- **Thật:** `hub.mjs` chạy như tiến trình con (`hub-process.mjs`), công cụ cục bộ, cổng phê duyệt, máy trạng thái, tệp trên đĩa, Git, pytest/uvicorn (bộ FastAPI), trình duyệt (bộ giao diện).
- **Giả:** *mô hình*. `mock-model-server.mjs` là một máy chủ nói theo kịch bản (`scenarios.mjs`: `call(tool, args)`, `calls(...)` cho nhiều lời gọi trong một lượt, `say(text)`, `thinking(...)`, `sequence(steps)`) và nói đúng giao thức thật: `/v1/chat/completions`, `/v1/messages` (Anthropic), `/v1/responses` và `/v1beta/models/<model>:generateContent` (Gemini), dạng JSON lẫn SSE (trừ Gemini). Nó từ chối điều API thật từ chối (kết quả công cụ sai chỗ, tham số lạ, khối thinking bị sửa; `protocol-validators.mjs` ghi nguồn của từng luật): Anthropic, Responses và Gemini mặc định chặt, còn Chat Completions chặt khi `strict: true` (`t.mock()` của khung E2E Node bật nó). Lỗi mạng bơm bằng `mock.inject({ kind: 'stall' | 'cut' | 'payload-too-large' | 'stream-unsupported' | 'status' })`. Bộ giao diện Playwright dùng `startMockModel()` không đổi (Chat Completions vẫn dễ tính).
- Vì vậy các bộ E2E chứng minh **Hub, công cụ và cổng quyền hoạt động cùng nhau**, *không* chứng minh một mô hình thật lập kế hoạch tốt. Điều đó cần khóa API: xem [TESTING-WITH-REAL-MODELS.md](TESTING-WITH-REAL-MODELS.md).
- Mọi bộ E2E kiểm tra **trạng thái cuối** (tệp trên đĩa, lần chạy test do chính bộ test thực hiện, các lần hỏi duyệt, checkpoint, nhật ký của nhà cung cấp), không tin lời mô hình hay giao diện.

Viết một bộ E2E mới:

```js
import { runScenario } from './e2e/harness.mjs';
import { answerApprovals, connectModel, setMode, startTask } from './e2e/hub-process.mjs';
import { call, say, sequence } from './e2e/scenarios.mjs';
import { gitInit, makeCalcProject } from './e2e/fixtures.mjs';

await runScenario({ name: 'mine', summary: 'what it proves', budgetMs: 120_000 }, async (t) => {
  const project = t.dir('app');
  makeCalcProject(project);
  gitInit(project, t.scratch);
  // Một kịch bản có sẵn ('repair-add', 'explore') hoặc tự viết bằng sequence():
  const mock = await t.mock({ scenarios: { mine: sequence([call('read_file', { path: 'calc.js' })], { final: 'Xong.' }) }, scenario: 'mine' });
  const hub = await t.hub({ project });          // một Hub thật (backend local) trên thư mục dữ liệu riêng
  await connectModel(hub, mock);                 // "Lưu & kiểm tra" như người dùng làm trong Cài đặt
  await setMode(hub, 'review');
  const task = await startTask(hub, 'Đọc calc.js rồi trả lời.');
  const { task: settled, answered } = await answerApprovals(hub, task.id, () => true);   // trả lời mọi yêu cầu duyệt
  t.equal(settled.state, 'completed', 'the task ends completed');
  t.equal(answered.length, 0, 'reading is never put to the person');
  // t.check(cond, label, detail) · t.equal(a, b, label) · t.must(cond, label) · t.note(text) · t.blocked(what, why) · t.skip(reason)
});
```

`runScenario` tạo thư mục tạm (đường dẫn dài, không phải 8.3), dọn Hub và thư mục tạm kể cả khi thất bại, đặt đồng hồ chống treo, in `ok`/`not ok` và `PASS:`/`FAIL:`, và đặt mã thoát. `t.hub({ stateDir })` với cùng `stateDir` mô phỏng khởi động lại. Một kịch bản là hàm chỉ nhìn thấy điều một mô hình thật nhìn thấy (yêu cầu của người dùng và kết quả công cụ đã gọi) và trả về bước kế tiếp; không có ngẫu nhiên, không có mạng.

## Kiểm thử đột biến

`tests/mutation/run-mutations.mjs` trả lời câu hỏi "bộ test này có **thật sự fail được** không?". Nó sao chép Hub vào thư mục tạm, hỏng mã **một chỗ nhỏ mỗi lần** (thay đúng một đoạn văn bản bằng đoạn khác: đổi điều kiện, xóa một lời gọi, tắt một lớp bảo vệ), chạy bộ test trên bản đã hỏng và báo bộ test có nhận ra không.

```powershell
cd CHATMCP-HUB
node tests/mutation/run-mutations.mjs tests/mutation/isolation.json
node tests/mutation/run-mutations.mjs tests/mutation/task-state.json --only M3,M4 --json out.json
node tests/mutation/run-mutations.mjs tests/mutation/fastapi.json     # cần Python như bộ FastAPI
```

| Kết quả | Nghĩa là |
|---|---|
| `KILLED` | bộ test fail trên mã đã hỏng — đúng như mong muốn (kèm tên các kiểm tra đã fail) |
| `SURVIVED` | bộ test vẫn xanh trên mã đã hỏng: lỗ hổng của test, hoặc dòng mã thừa. Công cụ thoát mã 1 |
| `EQUIVALENT` | đột biến không đổi hành vi (dòng phòng thủ thừa); danh sách ghi lý do bằng trường `equivalent`. Nếu nó lại bị `KILLED`, ghi chú báo "annotation is stale" |
| `ERROR` | đoạn văn bản cần thay không còn khớp **đúng một lần** (danh sách đã cũ hoặc mẫu mơ hồ) — không bao giờ coi là "đã giết" |
| `SKIP` | bộ test không chạy được trên máy này (ví dụ thiếu Python) nên không phán xét được; `--allow-skip` để chấp nhận |
| `N/A` | đột biến chỉ áp dụng cho hệ điều hành khác (trường `platforms`, tên theo `process.platform`): không chạy, không tính là sống sót, không đổi mã thoát |

Công cụ chạy bộ test trên bản **chưa hỏng** trước; nếu nó không PASS thì dừng (mã 2) vì mọi "KILLED" sau đó đều vô nghĩa. Tệp thật không bao giờ bị sửa — chỉ bản sao tạm. Mỗi danh sách chạy vài phút nên công cụ **không** thuộc `npm test`.

**Mã C# của vỏ và bộ cài.** `scripts/tests/native-lifecycle/run-mutations.mjs` làm điều tương tự cho `native-shared/`, `installer/` và `desktop-shell/`: sao chép chúng (cùng dự án test, các tệp mẫu dùng chung, `docs/WINDOWS-SETUP.md` và `scripts/tests/Test-NativeLifecycle.ps1`, vì bộ test C# chạy thật khối lệnh khôi phục bằng tay nằm trong tài liệu đầu và hàm `New-RetainedUpdate` nằm trong script sau) vào thư mục tạm, hỏng **một chỗ nhỏ mỗi lần** theo `scripts/tests/native-lifecycle/mutations.json`, **dựng** rồi chạy bộ test C# (khoảng 25–45 giây mỗi đột biến; cả danh sách mất vài giờ chạy tuần tự, nên không nằm trong CI; chạy song song nhiều phần bằng `--only` thì một phần có thể hỏng ở bài kiểm tra nền vì một bản sao `ChatMCP.exe` của phần khác vừa khởi động, nên chạy lại phần đó riêng). Một đột biến không biên dịch được là `INVALID` (một lỗi của trình biên dịch không phải là "bộ test đã nhận ra"), nên danh sách chỉ giữ đột biến dựng được; cũng là `INVALID` một đột biến loại `gate` hoặc `payload` làm tệp không còn phân tích được cú pháp (PowerShell báo `ParserError`, node báo `SyntaxError`): bộ phán xét hỏng vì tệp không còn là mã nguồn, không phải vì một kiểm tra đã nhận ra điều đột biến làm. Loại `"run": "gate"` chạy `tests/verify-update-apply.mjs` thay cho bộ test C# (hỏng tệp dự án, tên tài nguyên khóa, cửa sổ cập nhật, cách chạy bộ cài, điều kiện của trình duyệt hệ thống); loại `"run": "payload"` chạy `scripts/tests/Test-InstallerPayload.ps1`, các bài test PowerShell của chính bản dựng (bằng chứng rằng chương trình dựng ra mang đúng danh sách khóa, và việc hợp thức hóa đường dẫn cho MSBuild); KHÔNG BAO GIỜ thêm đột biến đổi bộ lọc đường dẫn của `CloseRunningProcesses` (bộ test sẽ yêu cầu ứng dụng DatGold đang cài trên máy đóng lại); `"needs": ["symlink"]` là đột biến chỉ máy tạo được liên kết tệp mới phán xét được (nơi khác là `N/A`, và test nói rõ là nó không chạy được ở đó); `"equivalent"` ghi lý do một đột biến cho cùng kết quả qua một kiểm tra khác. `--check` chỉ kiểm tra mọi mẫu còn khớp đúng một lần, không dựng; `verify-update-apply` làm đúng việc đó trong lần chạy Node thường nên danh sách không thể cũ đi mà không ai biết. Công cụ không bao giờ chạy bộ cài thật, Hub thật hay cổng 3007: bộ test C# chỉ dùng thư mục tạm và cổng loopback của riêng nó.
Danh sách có chừng 520 đột biến (cùng lý do của từng cái nằm trong tệp); mỗi lần có đột biến sống sót, nó được đọc với mã và với hành vi của .NET (thử bằng `dotnet fsi`) rồi hoặc ghi là tương đương kèm lý do, hoặc coi là lỗ hổng của test và lấp bằng test trước khi chạy lại đột biến đó. Kết quả có ngày tháng nằm trong mô tả của pull request, không nằm ở đây.

**Bản sửa `Recover` (`installer/InstallRecovery.cs`).** `scripts/tests/native-lifecycle/RecoverTests.cs` và `RecoverRefusalTests.cs` chạy nó trên những trạng thái mà một lần cập nhật dừng giữa chừng THẬT để lại: một tiến trình con của chính chương trình test (`CrashChild.cs`, `--crash-commit`) chạy một `InstallTransaction.Commit` thật rồi tự kết thúc bằng `Process.Kill` sau lần đổi thứ k (không có `finally`, không hoàn tác, như mất điện), nên dấu hiệu, nhật ký, bản sao lưu và các tệp thay dở đúng là cái giao dịch để lại; mỗi điểm dừng được tạo một lần và mỗi ca làm việc trên một bản sao. Chúng giữ: sửa đúng ở cả năm điểm dừng; dừng giữa chừng bản sửa ở từng bước rồi chạy lại; tệp đang bị giữ mở; thư mục sao lưu mồ côi; và một bảng các trạng thái của một tệp chạy qua hoàn tác thật của giao dịch và qua bản sửa với cùng một quyết định. Hơn năm mươi trạng thái hỏng, mỗi trạng thái bị từ chối bằng mã riêng và không đổi gì (dấu hiệu hay nhật ký rỗng, toàn số 0, không phải JSON hoặc quá cỡ; tên đi ra ngoài, qua junction, trong thư mục dữ liệu của Hub; bản sao lưu hỏng, thiếu, tên sai; chương trình chạy bản sửa nằm trong thư mục cài; tệp bị người khác sửa), nhật ký và dấu hiệu nguyên văn của các bộ cài 3.9.0–3.10.2 (ghi theo tên đường dẫn của máy khác) vẫn sửa được, và hàm `New-RetainedUpdate` của script vòng đời được chạy ở đây rồi bản sửa thật làm việc trên cái nó tạo (băm giả sẽ bị từ chối trên máy chạy CI). Script vòng đời (`Test-NativeLifecycle.ps1`, mục 2b) chạy bản sửa thật trên máy dùng một lần: từ chối khi một tệp bị sửa (qua nút Repair now của cửa sổ thật, qua dạng yên lặng và qua `--quiet --recover`) rồi khối lệnh trong hướng dẫn; nút Repair now trên trạng thái sạch (tệp kết quả `rolled_back` và ứng dụng cũ được mở lại; Hub của bản cơ sở không đọc tệp đó nên không hỏi nó); `--quiet --recover` hai lần.

Giới hạn trung thực của loại `gate`: ba đột biến `gate-window-keeps-itself-open-lost`, `gate-installer-handle-kept-after-look` và `gate-journal-not-flushed` chỉ bị giết bởi một kiểm tra **văn bản** trong `verify-update-apply.mjs` (nó đọc mã nguồn; không chạy cửa sổ, cũng không kiểm tra thứ gì đã xuống đĩa). Đường `Exited → launch_failed` trong `desktop-shell/MainWindow.Update.cs` (cửa sổ WinForms của vỏ) không có bài test hành vi nào: logic "nhìn installer trong 5 giây" của `UpdateApplier.WaitForInstaller` được test với một bộ "nhìn" giả, còn việc cửa sổ làm gì với kết quả ấy thì chỉ được kiểm tra bằng chữ. Danh sách đột biến không nên được đọc như thể nó phủ nhiều hơn thế.

Giới hạn trung thực: đây là một tập đột biến **nhỏ, viết tay** — chứng minh các bộ test đó bắt được những lỗi cụ thể này, không chứng minh chúng bắt được mọi lỗi. Các đợt đột biến thủ công khác trong quá trình phát triển (cho bộ sửa lỗi, Git, phục hồi phiên, kho độc hại) **chưa được lưu thành danh sách**. Để thêm đột biến: viết mẫu `old` (đúng một lần trong file), `new`, và `what`; chạy; nếu `SURVIVED`, hoặc sửa test, hoặc giải thích vì sao tương đương.

## Viết kiểm thử mới

- Tạo thư mục tạm bằng `fs.mkdtemp(path.join(os.tmpdir(), …))`; không bao giờ đọc/ghi thư mục trạng thái thật của Hub.
- Dùng `fileURLToPath(new URL(…, import.meta.url))`, **không** dùng `URL.pathname` (trên Windows cho `/F:/…`).
- Dọn dẹp bằng `await terminal.close()` *trước* `fs.rm(…)`; trên Windows tiến trình con giữ cwd sẽ gây `EBUSY`.
- Symlink file cần Developer Mode/quyền quản trị trên Windows (`EPERM`). Hãy thử symlink, nếu bị từ chối thì dùng junction thư mục và ghi rõ trong đầu ra (`note - … skipped`). Kiểm tra liên kết **file** vì thế chỉ chạy được trên Linux/macOS hoặc Windows có Developer Mode.
- Đừng giả định hành vi của tên file: trên Windows `.env ` (dấu cách cuối) không tồn tại được và bị từ chối bằng `bad_name`; `ENV~1` có thể là bí danh của `.env` (bị chặn bằng `protected_path`); `a:b` là đường dẫn theo ổ đĩa. Test phải chấp nhận *mọi cách từ chối an toàn* chứ không bám vào một mã lỗi của một hệ điều hành.
- Bí mật trong dữ liệu kiểm thử là giá trị giả có tiền tố rõ ràng (`FAKE-…`, `sk-adversarial-…`). Một test "không lộ bí mật" phải quét **tất cả** nơi bí mật có thể rơi vào (thư mục dữ liệu, nhật ký, transcript, yêu cầu mà mô hình giả nhận được) và nói số tệp đã quét, để "không tìm thấy" không phải lời hứa suông.
- Test hồi quy cho lỗi đã sửa phải **fail trên mã cũ**. Cách đã dùng cho các bộ E2E: *đột biến thủ công* — hỏng đúng dòng mã bảo vệ (đổi điều kiện, xóa một lời gọi), chạy bộ test, xác nhận nó **FAIL vì đúng lý do**, rồi hoàn lại. Một bộ test không thể fail là một bộ test không nói gì. Công cụ và các danh sách đột biến có sẵn: xem mục "Kiểm thử đột biến" ở trên.
- Một test không nên phụ thuộc đồng hồ: dùng `eventually(check, {timeoutMs})` thay cho `sleep` cố định.

## Quy ước Git

- Làm việc trên nhánh riêng (`dev/chatmcp-agent`), không push thẳng `main`, không force-push, không viết lại lịch sử khi chưa có sự đồng ý của chủ sở hữu.
- Commit nhỏ, một mục đích, kiểu Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`); thân commit nêu nguyên nhân, bằng chứng và điều *chưa* được kiểm chứng.
- Không commit: `node_modules`, state/transcript/log, bản sao lưu, ZIP, `.env*`, khóa, `deploy/.generated/`. Trước khi push: `git ls-files -ci --exclude-standard` phải rỗng.
- Cuối dòng: `.gitattributes` dùng `text=auto` — file đã commit với CRLF không bị viết lại; `.sh` luôn LF, `.ps1/.cmd/.bat` luôn CRLF khi checkout. Giữ script `.ps1` ở ASCII (Windows PowerShell 5.1 đọc file không BOM theo ANSI). Cảnh báo `LF will be replaced by CRLF` khi `git add` trên Windows là vô hại.
- Chạy `git diff --cached --check` trước khi commit.

## Đặc thù Windows cần nhớ

- Đường dẫn người dùng có thể chứa dấu cách và dạng ngắn 8.3 (`C:\Users\TENDAI~1\…`): so sánh đường dẫn luôn qua `fs.realpath`.
- Dừng cây tiến trình bằng `taskkill /PID <pid> /T /F`; trên POSIX gửi tín hiệu tới process group. Giết Hub bằng `TerminateProcess` không chạy handler nào: bộ `verify-e2e-recovery` mô phỏng đúng điều này.
- `$PSScriptRoot` dùng trong giá trị mặc định của `param()` trả về rỗng khi chạy `powershell -File` trên PS 5.1 — hãy tính trong thân script.
- Hàm PowerShell tên `Git` sẽ che `git.exe` và gây đệ quy vô hạn; đặt tên hàm có tiền tố.
- Pipe được thừa kế bởi tiến trình con: một dịch vụ nền khởi động từ Hub phải đóng stdio kế thừa, nếu không `Start` treo (đã sửa trong launcher).
- Đổi tên file đang bị chương trình diệt virus/trình lập chỉ mục giữ có thể báo `EBUSY/EPERM`: `lib/fs-safe.mjs` thử lại vài lần.
- Tiếng Việt trong đầu ra của bộ test có thể hiện thành `?` hoặc ký tự lạ khi console (hoặc công cụ điều khiển từ xa) dùng trang mã cũ như cp437/cp1252. Đó chỉ là hiển thị: mã thoát và PASS/FAIL không đổi, và tệp do `--json` ghi ra là UTF-8 nguyên vẹn. Dùng Windows Terminal hoặc `chcp 65001` để đọc. Chuyển hướng bằng `>` trong Windows PowerShell 5.1 sẽ ghi tệp UTF-16 và có thể làm méo chữ; dùng `--json` hoặc `cmd /c "node … > tệp.txt"`.

## Model-provider usage policy (Phase 1)

The user selects their compatible model API Base URL, API key, and model. DatGold does not implement a token allowance, usage reservation, dollar cap, or parallel-worker spending ledger. The provider is responsible for billing, credits and rate limits. Recorded token counts may be shown as diagnostics but never block further model requests solely because a DatGold spending threshold was reached. Optional explicit user-set step/time limits are supported, with unlimited defaults for normal coding model turns. Process concurrency, Windows Sandbox instance ownership, test retries, cancellation and execution timeouts remain safety controls, **not token/price quotas**.

DatGold is a standalone local desktop app; no IDE/VS Code integration is needed. PermissionGate supports explicit Full Access confirmation; it does not elevate the OS account or cancel Windows Sandbox isolation requirements for untrusted automated tests.

`dynamic-delegates.mjs` executes dynamically planned read-only subagents, started by the owner through the Hub API (the dashboard no longer has the form that did), through the same configured Gateway Provider and requires the literal `AUTHORIZE READONLY DELEGATION` confirmation. It has no internal token/spend budget; workers have no execution tools, and cancellation/restart are explicit.

## Cached and reasoning-token usage diagnostics

Agent tasks now preserve provider-reported cache hits, cache writes and
reasoning tokens separately from total input/output. Prompt caching (`cache_control`)
is requested from endpoints known to accept it, a `promptCaching` flag in `lib/provider-presets.mjs`: the `anthropic` preset and any connection or model profile aimed at api.anthropic.com; compatible gateways remain conservative.
OpenAI-compatible Chat Completions and Gemini include cache and reasoning
telemetry when returned by the provider. Missing or zero usage fields are
**unknown or zero as reported**, not verified billing savings. Reports and
conversation UI disclose this telemetry without imposing quotas.

## Reproducible parity metrics (grades are user-provided)

Run `node tests/benchmarks/summarize-parity.mjs results.json` from
`CHATMCP-HUB`. The input must be a JSON object:
```json
{
  "schema": 1,
  "cases": [{
    "id": "bug-001",
    "baseline": {"grade":"pass","httpRequests":5,"inputTokens":1000,"outputTokens":500,"durationMs":60000},
    "candidate": {"grade":"pass","httpRequests":3,"inputTokens":900,"outputTokens":450,"durationMs":60000}
  }]
}
```
Use the same tasks, model class, hardware, test budget and repeats for
both runners. Grades must be supplied by an external test/evaluation
process. The aggregator validates numeric fields, reports the success
ratio and request/token usage per successful task, but does **not**
cryptographically verify grades, run hidden tests, invoke a model,
or certify parity with Codex/Claude. At least 100 tasks are recommended;
reported sample-count adequacy is not proof of statistical validity.
