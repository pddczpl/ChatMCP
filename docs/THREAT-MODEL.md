# Threat model: Hub credential, Companion outbound filter, Read Only classifier, lifecycle hooks

Scope: DatGold 3.9.0 plus the phase-P0 changes. It covers the three attack surfaces that phase P0 added or rebuilt: the per-launch credential of the local Hub, the outbound filter and review hold of the ChatGPT Web Companion, and the Read Only command classifier. Phase P1 adds a fourth, the lifecycle hooks (Surface 4), a fifth, what a parent agent reads about the agents it started (Surface 5), and a sixth, the third-party text that is loaded into the prompt on purpose: project instruction files and skills (Surface 6). Phase P3 adds a seventh, the list of models the Hub plans from and the one request it can make to update it (Surface 7). The in-app updater adds an eighth with its three steps: the notice that a newer release exists and the requests the Hub can make to find out, the signature on the release manifest, the download of the installer on the owner's click, and, in the desktop app and again on the owner's click, the installation of what was downloaded (Surface 8). It builds on [SECURITY.md](../SECURITY.md) (the policy), [HUB-AUTH.md](HUB-AUTH.md), [COMPANION-PRIVACY.md](COMPANION-PRIVACY.md) and [ARCHITECTURE.md](ARCHITECTURE.md), and does not repeat them. It is written for one trusted owner on one Windows account; public or multi-tenant deployment is out of scope.

Every statement about code names a file and a symbol in the [code reference table](#code-references), written `[C7]`. `tests/verify-threat-model.mjs` checks that each file exists, that each symbol is in it, that each reference is used, and that this document and `SECURITY.md` state the same limits. A claim that no test exercises is marked **not tested**.

## The limit that decides everything else: same OS user

The Hub's per-launch secret is stored in `<data folder>/run/hub-session.json` [C3] [C4]. **Any process that runs as the same Windows user can read that file.** The desktop app, the launcher scripts and the installer read it, so nothing in the design can stop another program with the owner's rights from doing the same. The bearer therefore protects against:

- other Windows accounts on the same computer (the folder carries an ACL that grants only the owner's SID);
- sandboxed processes that cannot read the owner's files (low-privilege or restricted tokens);
- web pages and other browser origins (they cannot read the file, cannot set an `Authorization` header across origins without a CORS grant, and the Hub grants none to web origins).

It does **not** protect against malware or any other program running as the owner. Such a program can also read the workspace, the key store and the owner's browser profile directly; the Hub secret adds nothing for it. This is a stated boundary of the product, not a defect to be closed by more checks. Two exceptions inside the first bullet are listed below as risks RR-2 and RR-3.

## Surface 1: the per-launch Hub credential

Flow in one paragraph. `main` makes a fresh 32-byte secret, removes `CHATMCP_HUB_SECRET` from its environment so that no child process inherits it, registers it with the log redactor and binds `127.0.0.1` only [C1] [C2]. It writes the session file after fixing the folder ACL [C3] [C4]. `createHubServer` then applies, in order, the Host check, the Origin check, one default-deny bearer gate for every `/api/*` and `/auth/*` request, and CSRF checks on mutations [C5]. A native or Node client, or a PowerShell helper script, that finds a Hub already running reads the session file and presents the secret only after the process that listens on the port is the one the file names [C12] [C13] [C26] [C27]. A dashboard receives the secret through a 60 second, single-use ticket in a URL fragment [C9] [C11].

## Surface 2: outbound filter and review before send

Everything the agent reads for a task and sends through the Companion goes into the owner's ChatGPT chat (A4, X8). The Hub scrubs and, optionally, holds that traffic before the extension can fetch it.

- **Scanner.** Text that has the shape of a credential is replaced by `[REDACTED:<label>]` [C15]. It runs on the tool result object before it is turned into text and paged, on prompts, handoff and continuation text, and again when a message is built or shown, so `poll()` and `claim()` never hand out a credential shape [C15] [C17].
- **Protected files.** A call or result that names `.env*`, `*.pem`, `*.key`, `id_rsa*` or another protected path is replaced as a whole by a short notice; the tool itself still ran [C16] [C23].
- **Review before send** (off by default, global or per workspace). A result is created in status `held`; `poll()` does not offer it, `claim()` refuses it, no timer sends it, and the owner chooses Approve, Redact more or Withhold. Ten minutes without a decision, or cancelling the task, ends the task with nothing sent and marks the delivery unverified so the resumer does not continue on its own [C17].
- **Ledger.** The task record keeps labels, counts and withheld file names, never a matched string [C18].

| ID | Threat | Mitigation | Test | Limit |
|---|---|---|---|---|
| O1 | A secret-shaped string reaches chatgpt.com | scanner on every outbound text path [C15] | `verify-outbound-redaction.mjs` (every credential format of its corpus, and the benign corpus must stay unchanged), `verify-outbound-runner.mjs` (real runner, what `poll()`/`claim()` return) | pattern-based: a secret with no recognisable shape, anything in an image or binary, and anything that is confidential only for a client are not caught |

| O5 | The ledger itself leaks a secret | labels and counts only; file names pass the scanner and are cut to 80 characters [C18] | `verify-outbound-runner.mjs` | none known |

## Surface 3: the Read Only classifier

In Read Only mode `PermissionGate` refuses every call whose category is not `read` or `checkpoint`, without asking [C24]. For `run_command` the category comes from the command text: `analyzeCommand` splits it into segments and gives each a kind (`read`, `verify`, `edit`, `exec`, `dangerous`) [C19] [C25]. A program counts as `read` only when `analyzeReadProgram` finds **every** option on that program's allowlist [C20]; `sed` additionally needs a script the strict grammar accepts [C21]. Anything unknown is `exec` and is refused in Read Only. A command the text analysis would let through then gets a second look at the file system: arguments that resolve outside the project, to a protected file, or through a junction raise it to `exec` [C22] [C23]. Tool descriptions and a provider's `readOnlyHint` are never trusted [C24].

| ID | Threat | Mitigation | Test | Limit |
|---|---|---|---|---|
| R1 | A "read" program writes or runs code through an option (`sed e/w/r`, `sort -o`, `uniq IN OUT`, `file -C`, `rg --pre`, `find -fprint`, `tree -o`, `less +cmd`, `date -s`) | per-program option allowlist, strict `sed` grammar [C20] [C21] | `verify-readonly-corpus.mjs` (attack corpus through the real classifier, gate and tools, with a positive control) | the corpus is written by the same author as the classifier; it shows the listed bypasses are closed, not that none exists |
| R2 | Redirection, command substitution, chaining or PowerShell aliases hide a write | tokenizer and per-segment analysis, alias table [C19] [C20] | `verify-command-analysis.mjs`, `verify-readonly-corpus.mjs` | shell grammar is re-implemented, not delegated to a shell |
| R3 | A wildcard expands to an option or to a secret; a junction leads out of the project | file-system pass after the text analysis [C22] [C23] | `verify-readonly-corpus.mjs` (needs-file-system cases) | the expansion is evaluated at check time; a change between the check and the run (race) is **not tested** |
| R4 | Reading a protected file or a file outside the project | protected-path rules in the read tools and the command pass [C23] [C22] | `verify-readonly-corpus.mjs` (protected file below a searched directory, outside the project) | Read Only still lets the model read project files and send them to the provider (X8) |
| R5 | A tool claims it is read-only | name-based classification, hints ignored [C24] | `verify-permissions-modes.mjs` (modes); the rule that a provider hint never lowers a category is **not tested** | none known |

The classifier reads command text. It is not an operating-system boundary: whether an allowlisted program can be made to write through the environment or through a configuration file that another process set is not established by the corpus (**not tested**).

## Surface 4: lifecycle hooks

Hooks are programs the owner configured that the Hub starts around a tool call; the format and behaviour are in [HOOKS.md](HOOKS.md). The owner writes `<data folder>/hooks.json`; a project may ship `.chatmcp/hooks.json`. `HookRunner` reads both on every call. It runs the owner's file as written and the project's file only while its sha256 is the one the owner approved, for that folder [C28]. The guard that every tool call passes asks the permission gate first, then the PreToolUse hooks, and only then makes a checkpoint and runs the tool; PostToolUse hooks run after it, and nothing they do can change what the tool did [C29]. A hook is started with a scrubbed environment, in a process tree that a timeout, a cancel or a shutdown kills, and its stdout is cut at 64 KB [C28] [C30]. What it prints is read through a fixed list of fields: it can refuse a call or ask the owner about it, and the gate's `forceAsk` can only add a question, never remove one or turn a refusal into an approval [C31]. A spawned agent, a coding worker and the ChatGPT Web Companion reach their tools through the same guard and share the one runner [C29]. The patterns of an if rule and the wildcards of a command operand that may name the hooks file are matched by a table walk whose cost is bounded by the lengths of the pattern and the text, never by a regular expression made from them [C33]. `.chatmcp/hooks.json` is a protected path, so the file tools refuse it [C23]; the approval route sits behind the Hub bearer [C32].

Three of the events fire when an agent run ends with a final answer: `Stop` (`SubagentStop` for an agent that a model or the coding orchestrator started) and, once the Hub has computed its own assessment of the evidence, `TaskCompleted` [C34] [C35]. A hook can send the agent back to work (exit 2, or `{"decision":"block"}`) and nothing more: whatever the model then does passes the permission gate as before, within the run the hook's text reaches the model only as a labelled host message written through the history ledger (never as a prompt, so it selects no tool and no skill; afterwards it survives only as recorded task data: an event line and the notice in the result), and the refused answer, its verification outcome and the final text are not kept on the running task [C34] [C35]. The agent can be sent back at most 8 times per run, the three events together; the next objection ends the run with a visible note [C34]. These events fail open: a hook that crashes, hangs, is missing or whose file is invalid does not stop a task from completing, and the task log says so [C34]. The ChatGPT Web transport and the single-request helpers have no loop and fire none of them.

## Surface 5: what a parent agent reads about the agents it started

A model that starts background agents (`spawn_agent`, `spawn_workflow`) can read what they produced with `agent_results`, and the Hub tells it, in a message it writes itself, when one stops. What an agent wrote is model output that has read repository text, skills and web pages (X7), so it reaches its parent as data and never as a message of the user's. The tool answers from the Hub's records of the caller's own children only, as JSON in which the agent's final message is one string under `claim` (`verifiedByHub: false`) and what the Hub recorded is a separate object, `hubRecord`; the Hub's own sentences (the "verification notice" and the note about a hook that still objected) are taken out of the claim, by the boundary the runner recorded where it made the final text, and reported with the record [C51]. The answer is bounded, is redacted with the runner's secrets and the outbound scanner before it is cut, and holds nothing that changes between two calls while an agent only waits [C36]. The call is read-only, recorded as such while it runs, and outside the permission gate and the hooks like the spawn calls [C37]. The notice holds the Hub's facts (ids, how each agent stopped, when) and the goal the parent itself wrote, quoted on one line; it holds nothing an agent wrote. It is added behind every result of a model turn, as a host message of its own kind, and never to the prompts, the conversation or the texts the tool and skill selection reads, so it can neither select a tool or a skill nor count as something the user asked [C38]. What the parent keeps about an ending is a bounded list in its task file, validated again when the task is loaded [C39].

## Surface 6: project instructions and skills on demand

Two kinds of third-party text reach the model's prompt on purpose (X7): the `AGENTS.md`, `CLAUDE.md` and `.claude/CLAUDE.md` of the workspace, which whoever owns the repository wrote, and the skills the owner installed, which may come from a registry. Both are bounded, cleaned, labelled as untrusted and recorded; neither is read by the permission gate, which decides on the tool call alone [C24].

**Project instructions.** At the start of every run `loadProjectInstructions` reads three fixed names from the root of the workspace, in this order, and nothing else: no nested file and no file above the workspace [C40]. A file is opened only when its real path (links and junctions resolved) is inside the workspace and is not a protected file, it is a regular file of at most 256 KiB (a larger one is never opened), and it is UTF-8 or UTF-16LE with a byte order mark; the read asks for one byte more than the limit, so a file that grew in the meantime is refused. The text loses its BOM, its CR LF and its invisible characters (tag characters, zero-width and bidi controls, escape and control codes), is masked by the runner's own redactor (the one every tool result goes through) and only then is measured [C41]. The block that is built, headers, fence and truncation markers included, is at most 8,192 bytes and, where the room of the run is small, a share of its planned history (10%, and with the skill index at most 15% together and half of what is left above the 1,000-token floor, whatever the window and also when it is unknown) [C47], and the first file fills the room; it goes into the agent's *instructions*, between the Hub's own rules and the tool list, labelled as untrusted project text that cannot grant or skip a permission, and ended by a line that carries an id made from the text itself, so a file cannot contain the line that closes its own block [C40] [C42]. Each run records what was loaded (paths, status, sizes, sha256 of the file and of the block, never a text) and the owner can switch the loading off [C43]: in Settings, a saved choice that applies from the next run of every runner (the foreground one, a pooled chat and a coding worker, whichever already exist), or with `CHATMCP_PROJECT_INSTRUCTIONS`, which is stronger and which a click never changes. The route that saves the choice sits behind the bearer like every route and takes nothing but true or false [C48] [C49] [C50]. Off means only that the Hub does not put the files into the instructions: the agent is then told to read the project rules itself and a read is allowed in every mode, so the same untrusted text can still reach the model, as a tool result (RR-22).

**Skills.** The conversation carries an index of the selected skills of at most 4,096 bytes (5% of the planned history with the definition of `skill_load`, which is paid out of it [C47]; a skill the share cannot offer is dropped and the activity log says so): a skill of at most 1 KiB whole, indented under its header so that no line of it can look like a header, a bigger one as a line that names `skill_load`; names, licences and descriptions are cleaned to one line each and masked [C44]. `skill_load` is a host function: it returns the text of one selected skill once per load, at most 16 KiB, labelled as untrusted data, redacted by the runner like any result, and records a receipt with the hash of the skill as installed and of what the model was given [C45]. It decides nothing and is not passed through the permission gate or the hooks, like `spawn_agent` [C46].

## Surface 8: the notice that a newer release exists, the signature on its manifest, the download of its installer and its installation

Steps 1 and 2 of the in-app updater tell the owner that a newer release exists, check the signature on its manifest and, on the owner's click, download its installer into a folder of the Hub's own; the Hub installs and runs nothing, and never opens or moves the finished installer. Step 3, the installation (the second paragraph below and rows U15 to U22), happens in the desktop app only. In a check the Hub reads two addresses. The first is `https://github.com/pddczpl/ChatMCP/releases/latest/download/RELEASE-MANIFEST.json`: GitHub answers it with two redirects (github.com, then release-assets.githubusercontent.com) to the manifest of the Latest release that is not flagged as a pre-release, so a test build never reaches anyone [C62]. The second is the signature of the release that manifest names, `https://github.com/pddczpl/ChatMCP/releases/download/v<version>/RELEASE-MANIFEST.json.sig`, which the Hub builds from the validated version and never from a link in an answer; a 404 there means "not signed yet" [C69]. A click on Download adds a third address, the installer, built from the version and from the file name in the signed manifest [C70]. Every request is a GET with `Accept` and `User-Agent: DatGold/<version>` and nothing else that identifies the person; GitHub sees the owner's network address and that a DatGold of that version runs. Whether the Hub looks on its own is the owner's choice, in three states: yes, no, and not answered yet. Until the owner answers, the Hub makes no request of its own and the page asks once; what "not answered" means is one constant, `WHEN_UNANSWERED` (today `ask`), and what it should be is the owner's decision [C64]. **Check now** is the owner's own act and works in every state. Once the owner has said yes, the Hub asks 30 seconds after it starts and then every 12 hours (1 hour after a failure), each with jitter, never within 15 minutes of the last attempt (the attempt is saved before the request goes out, so a Hub that restarts in a loop still asks once per 15 minutes; where it cannot be saved, the Hub does not look on its own), and a manual check is answered with a request at most once a minute; a time ahead of the clock (a clock that was fast, or was put back) counts as now, so it cannot hold either for hours [C64]. What comes back is data: at most 64 KiB in 10 seconds, strict JSON of a known shape, a release version x.y.z and never a pre-release; the notice is offered only for a version strictly higher than the one that runs, and the link to its notes is built from that version by the Hub and checked again by the page [C63] [C65] [C66]. The signature file is at most 4 KiB; it is ECDSA over P-256 with SHA-256 (IEEE P1363, 64 bytes), made over the exact bytes of the manifest, and it is checked against the public keys in `CHATMCP-HUB/lib/release-keys.json` (at most 4; only entries marked for release are trusted, so the placeholder that ships until the owner has made a key trusts nothing) [C67] [C68]. A download starts only from the owner's click on Download (a POST that carries a version and nothing else, except that Download again, which the page offers after the desktop app found the downloaded folder gone or not proving itself, adds `again: true`, which drops what the Hub calls ready and fetches it anew with every other check of the click still made), never from a timer, at start-up or after a check, and it is allowed while tasks run: the Hub fetches the manifest again by its tag, checks the signature again, takes the name, size and SHA-256 of the installer from that manifest and from nothing else, needs twice the installer's size free, takes at most 2 GiB, gives up after 60 seconds without a byte, and keeps the file only if its size and SHA-256 are the signed manifest's [C69] [C70] [C71] [C72]. What the page offers follows from that and from nothing else [C75].

Step 3 is a second act, with its own click. Nothing is installed or run unless the owner clicks Install and restart in the desktop app. An installation starts only from the owner's click on Install and restart: the page draws that control only when it runs inside the desktop shell (a plain browser is told where to do it and has no control), only for a download that is ready, and holds it back with its reason while a task, a terminal or a worker runs; it asks once more before it sends anything, and the question and a refusal belong to the release the owner pressed the button for [C87]. Everything that matters is decided by the shell with its own code [C85] [C77]. It must be a copy that the installer made. It asks the Hub, with the session secret, whether it is doing work and which version it has ready (a state whose `agent` is missing, or is not an object, counts as work), and asks again after the file is hashed; the version the Hub offers in that second answer must be the one the folder holds (`stale`). It finds the folder itself, under the Hub's data folder: at most 16 release folders are looked at and exactly one must prove itself, which it does only if the signature of the kept manifest checks against the keys built into the program (the file the Hub reads, embedded when the program is built; while it holds only the placeholder the shell trusts nothing and refuses), the version in the manifest is the folder's name and newer than the one that runs, and the installer's name, size and SHA-256 are the signed manifest's, the file being hashed through a handle that stays open until the program has been started (and the program being started from the real place of that handle, not from the path that was walked to find it) and carrying the product and description names of the DatGold setup [C78] [C84]. The installer, in update mode, waits at most 30 seconds for the app to close (and not at all for a process id that has become another program), refuses an installation that is not older than itself, an earlier update that did not finish and a disk without room, notes which shortcuts there are before anything is replaced, replaces the files in one transaction that rolls back on an error, shows a window with a bar that claims no percentage and no button, writes a result file, but only when no program listens on the port of the Hub (the Hub reads it once, when it starts, so a note left beside a Hub that is already up would be read by nobody until some later start), and opens the right app again: the new one after an update, the old one after a refusal or a whole rollback, none while the installation needs recovery; its window says "opened again" only when the app really was opened [C80] [C81] [C89].
