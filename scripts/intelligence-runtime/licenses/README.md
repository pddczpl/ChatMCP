# Vendored licence notices

Two groups: the notices of the bundled Tree-sitter grammars (the `*.LICENSE` files here) and the notices of what is compiled into `rg.exe` (the `ripgrep/` folder, described at the end).

## Tree-sitter grammars

`stage.mjs` copies the files below to `licenses/<project>/LICENSE` in the staged runtime, which `Build-Installer.ps1` ships as `CHATMCP-HUB/licenses/`. `notices.mjs` lists them (`GRAMMAR_NOTICES`).

| Vendored file | Upstream project | Compiled into |
|---|---|---|
| `tree-sitter-javascript.LICENSE` | <https://github.com/tree-sitter/tree-sitter-javascript> | `grammars/tree-sitter-javascript.wasm` |
| `tree-sitter-typescript.LICENSE` | <https://github.com/tree-sitter/tree-sitter-typescript> | `grammars/tree-sitter-typescript.wasm`, `grammars/tree-sitter-tsx.wasm` |
| `tree-sitter-python.LICENSE` | <https://github.com/tree-sitter/tree-sitter-python> | `grammars/tree-sitter-python.wasm` |

Each file is the project's own `LICENSE` file, copied unchanged from the upstream repository (`tree-sitter-wasms` 0.1.13 declares `^0.20.3`, `^0.20.5` and `^0.21.0` as the development dependencies it built the grammars from; the exact versions are not recorded in the package). A file is accepted only when it has a copyright line with a year and the MIT permission paragraph; anything else counts as missing.

These three files were copied unchanged from the default branch of each upstream repository on 2026-10-19 (`gh api repos/tree-sitter/<project>/contents/LICENSE`): tree-sitter-javascript (Copyright (c) 2014 Max Brunsfeld), tree-sitter-typescript (2017 Max Brunsfeld), tree-sitter-python (2016 Max Brunsfeld). The upstream default branch may be newer than the grammar builds inside `tree-sitter-wasms` 0.1.13; the copyright lines of these projects have not changed, but the grammar versions are not recorded in the package.

If one of them is missing or unusable:

- `stage.mjs` stops, so `Build-Installer.ps1` and the release workflow fail with a message that names the missing files.
- A build that is not a release may set `CHATMCP_ALLOW_PENDING_NOTICES=1` (no workflow does). It stages `licenses/PENDING-NOTICES.txt`, records `pendingNotices` in `runtime-manifest.json` and prints a warning.
- `tests/verify-notices.mjs` prints which notices are pending (none when all three files are present) and fails if a release workflow sets the variable, and if any workflow does while all three files are present.

## What is compiled into rg.exe (`ripgrep/`)

`rg.exe` is staged from the official ripgrep archive by `stage-ripgrep.ps1`. The archive carries the texts of ripgrep itself (`LICENSE-MIT`, `UNLICENSE`, `COPYING`) and nothing else, but the binary is statically linked with PCRE2 (BSD-3-Clause, which asks for its notice in binary redistributions), with Rust crates and with the Rust standard library of the toolchain that built it. Their texts are vendored in `ripgrep/`, and `stage.mjs` copies them, with the inventory, to `licenses/ripgrep/` in the staged runtime, which `Build-Installer.ps1` ships as `CHATMCP-HUB/licenses/ripgrep/`.

- `ripgrep/MANIFEST.json` is the inventory. `subject` names the release and the SHA-256 of the archive it was derived for. `basis` says how it was derived. `workspaceCrates` are ripgrep's own crates, covered by the archive's texts. `notLinked` are the packages of ripgrep's `Cargo.lock` that are not part of `rg.exe`, each with the reason. `components` are PCRE2 and the crates that are, each with its license expression and its texts: path, kind, size, SHA-256 and where the text came from (repository, tag, commit, path and the git blob id, which anyone can compare with `github.com/<repository>/blob/<commit>/<path>`). `rustStd` is the Rust standard library: `toolchain` (the nightly of 2026-07-15, its `rustc` version string and the commit of rust-lang/rust, with how they were derived), `lockfile` (`library/Cargo.lock` of that commit), `linked` and `inTree` (what `std` links for this target), and `notLinked` (the other registry packages of that lock file, each with the reason). Its components have the type `rust-library` (the root texts of the commit), `rust-library-part` (a subtree of `library/` with notices of its own) or `crate` with `origin: "rust-std"` (a registry crate that `std` links; `cfg-if` is shared with ripgrep and has one entry).
- `ripgrep/<component>/<file>` are the texts, copied unchanged from the upstream repository. `.gitattributes` marks the folder `-text`, so no checkout changes a byte (on a Windows runner `core.autocrlf` would break every hash).
- A text is accepted only when it is non-empty, has the SHA-256 and git blob id of the inventory and says what its `kind` says (`mit`, `apache-2.0`, `unlicense`, `bsd-3-clause`, `unicode`, `unicode-3.0` for the Unicode License V3 of `core`, `pcre2`, `compiler-builtins` and `libm` for the two composite files of `compiler_builtins`, plus `pointer` for a short COPYING file that names the licenses and `notice` for a COPYRIGHT file). The judge reads words, not line breaks, and asks for no copyright line: several upstream MIT texts (anyhow, serde, zmij) have none. A component's license expression decides which kinds it needs (`MIT OR Apache-2.0` needs both texts; an identifier that `notices.mjs` does not know is an error).
- There is no pending option here: `stage.mjs` stops when the inventory or a text is missing or changed, and when `stage-ripgrep.ps1` pins another release or archive than `subject` (a new ripgrep means deriving the inventory again). `verify.mjs` requires every text and the inventory in the staged runtime and the installed payload, each with its vendored hash. `Build-Installer.ps1` calls `Assert-InstallerRipgrepNotices` on the payload, and `test-runtime.mjs` checks the inventory against the real `rg.exe` of the installer build: the version string that the PCRE2 library carries (`compiledVersionString`, `10.46 2025-08-27`) must be in the bytes of the file, and `rg --pcre2-version` must print what `rgReports` records; the bytes must also carry `/rustc/<commit>` followed by `/` or `\` for the commit of `rustStd.toolchain` (the source paths that `core` and `std` leave in every binary; a binary that carries other commits is refused and they are named), and the import table of the PE file must name no C runtime DLL (`checkStaticCrt` reads it; the notices say that the C runtime is linked statically). `tests/verify-notices.mjs` and `scripts/tests/Test-InstallerPayload.ps1` check all of this, and `tests/verify-notices.mjs` also checks the rows in `THIRD-PARTY-NOTICES.md` and `DATGOLD-HUB/THIRD-PARTY-NOTICES.txt`.

### How the inventory was derived (2026-10-25, ripgrep 15.2.0)

Nothing was downloaded from crates.io except JSON metadata, and no binary or installer was downloaded or run.

1. **The build.** `.github/workflows/release.yml` at tag 15.2.0 builds the Windows binary with `cargo build --profile release-lto --features pcre2 --target x86_64-pc-windows-msvc` and `PCRE2_SYS_STATIC=1`; `.cargo/config.toml` adds `-C target-feature=+crt-static`.
2. **The crates.** ripgrep's `Cargo.lock` at the tag has 59 packages (`basis.lockfile`: commit, blob id, SHA-256). The checksum of every registry package equals the one in the crates.io index. The dependencies of each package (kind, `cfg(...)` target, optional, features) come from that index and from ripgrep's workspace manifests; the normal dependencies of the `ripgrep` package, with the `pcre2` feature, for x86_64-pc-windows-msvc (`windows`, `target_env = "msvc"`, `crt-static`, release profile), were followed with Cargo's feature rules. Result: 10 workspace crates, 30 registry crates and 19 packages that are not linked (development and build dependencies such as `regex` and `cc`, optional crates no feature reaches, `tikv-jemallocator` for musl only).
3. **PCRE2.** `pcre2-sys` 0.2.10 bundles the sources and its `update-pcre2` fetches PCRE2 10.46; `include/pcre2.h` in the crate says `PCRE2_MAJOR 10`, `PCRE2_MINOR 46`. The crate does not bundle PCRE2's license, so the text is `LICENCE.md` of PCRE2Project/pcre2 at tag `pcre2-10.46` (the same bytes as at `pcre2-10.45`). Note that `rg --pcre2-version` prints `PCRE2 10.45`, not 10.46: `pcre2::version()` returns the `PCRE2_MAJOR` and `PCRE2_MINOR` constants of `pcre2-sys/src/bindings.rs`, which were generated for 10.45 and not regenerated when the bundled sources went to 10.46. The installer build of the first version of this inventory (derived from the sources alone) stopped on exactly that, which is why the inventory records both numbers (`rgReports`: what rg prints; `compiledVersionString`: what the compiled library carries, `pcre2_config.c` builds it from `pcre2.h`) and why the check that ties the notice to the binary is the search for the second one in the bytes of `rg.exe`. The number it prints also says which `pcre2-sys` built the binary: the bindings and the bundled sources agree in 0.2.8 (42) and 0.2.9 (43) and only 0.2.10 has 45 against 46, so a binary that prints 10.45 was built with 0.2.10, the version in the lock. The technique of the byte search was tried first on another MSVC build of ripgrep with PCRE2 (a copy bundled with an editor): its `.rdata` carries the same literal, once.
4. **The texts.** For each crate, the license files of the upstream repository named on crates.io, at the commit of the tag of that version (`windows-sys` and `windows-link` have no tag: the windows-rs commit "Release 71" that set these versions), read through the git objects with the GitHub API; the git blob id was recomputed from the bytes. Beyond the files at the top of a crate's folder: the Unicode license of `bstr`, `regex-syntax` and `regex-automata`, and the license of the C++ project that `zmij` ports.
5. **The Rust standard library (`rustStd`).** ripgrep's release workflow builds with `nightly` and does not pin it: there is no `rust-toolchain` file at the tag and the `dtolnay/rust-toolchain@master` step requests no components. `rustStd.toolchain` records what the release record says: run 29431117779, job `build-release (win-msvc, windows-latest, nightly, x86_64-pc-windows-msvc)` started 2026-07-15T16:07:59Z; the nightly manifests `dist/<date>/channel-rust-nightly.toml` were published 2026-07-14 01:27:58Z, 2026-07-15 01:29:39Z and 2026-07-16 01:30:20Z, so `nightly` was the one of 2026-07-15, whose `[pkg.rustc]` says `version = "1.99.0-nightly (da80ed070 2026-07-14)"` and `git_commit_hash = "da80ed0708a09dc096c184345d6eb42cbcd50a1e"`. The toolchain was not downloaded; the texts of rust-lang/rust were read through the git objects of that commit. Rust's `COPYRIGHT` there lists no third-party text: it says that licenses are tracked with REUSE (`REUSE.toml`, `license-metadata.json`, the cached output of the `reuse` tool, and `LICENSES/`) and with cargo, and that `src/tools/generate-copyright` collects both into `COPYRIGHT-library.html`, which ships only in the `rustc` component of a toolchain (bootstrap `dist.rs`) and was not downloaded. So the inventory is built from the same inputs. Under `library/`, `license-metadata.json` names the Unicode tables of `core` (Unicode-3.0), `backtrace` (a git submodule: its texts are those of the pinned commit of rust-lang/backtrace-rs), `std/src/sync/mpmc` (the copyright of The Crossbeam Project Developers: the texts are crossbeam's, at the tag `crossbeam-channel-0.5.17`) and a Fuchsia mutex that is not compiled for Windows; the subtrees `compiler-builtins` (with `libm`), `stdarch` and `portable-simd` carry license files of their own. The registry crates that `std` links for x86_64-pc-windows-msvc were read from `library/std/Cargo.toml`, `library/sysroot/Cargo.toml`, `library/unwind/Cargo.toml`, `library/compiler-builtins/compiler-builtins/Cargo.toml` and `library/Cargo.lock` (49 packages): `cfg-if`, `hashbrown` and `rustc-demangle`. `libc`, `miniz_oxide`, `addr2line`, `object` (and so `gimli`, `adler2`, `memchr`) are gated off for this target, where backtraces use `dbghelp`; `foldhash` is reached only through a feature that `std` switches off. The locked checksums of the three linked crates equal the crates.io index. The 27 other registry packages are in `rustStd.notLinked` with the reason.
6. **The Microsoft C/C++ runtime components.** The terms were read on 2026-10-25 and are summarised in `THIRD-PARTY-NOTICES.md` (section "Microsoft C/C++ runtime components"); no Microsoft text is vendored. What was read, with the file hashes: the license terms of the Windows SDK as installed with SDK 10.0.26100.0 and 10.0.28000.0 (`Windows Kits\10\Licenses\<version>\sdk_license.rtf`, identical, SHA-256 `0f4a26ac9dc50066f8a1bfeaaf3f092d1b9e4791df5487b9f3c31e7c3dc4d7f5`) and the REDIST.TXT list <https://learn.microsoft.com/en-us/legal/windows-sdk/redist> (updated 2024-10-21; section "Static LIB files"); the Visual Studio 2022 Enterprise and Professional terms (<https://visualstudio.microsoft.com/wp-content/uploads/2021/11/Visual-Studio-2022-Enterprise-Professional-License-EN.docx>, SHA-256 `9c0cd52b20db9d081854c75bd1b50c75514b8f8cb09c8cad15e89d90b97b5bf3`) and Visual Studio 2026 terms (<https://visualstudio.microsoft.com/wp-content/uploads/2025/10/Visual_Studio_2026-License-Enterprise_Professional_ENU.docx>, last updated 2025-10-01, SHA-256 `dd2ab92a7c2bb90dd509e16572707a34b13bc0bc09b9199d115f25594ac39053`), section "Distributable Code"; the Distributable Lists of Visual Studio 2022 and 2026 (<https://learn.microsoft.com/en-us/visualstudio/releases/2022/redistribution>, <https://learn.microsoft.com/en-us/visualstudio/releases/2026/redistribution>, both dated 2025-11-11); "Redistribute Visual C++ Files" (ms.date 2026-04-13); "C runtime (CRT) and C++ standard library (STL) lib files" (ms.date 2021-03-05), which says that `libcmt.lib`, `libvcruntime.lib` and `libucrt.lib` are the statically linked CRT of `/MT` and that the static library of the UCRT is in the Windows SDK; and the license of the redistributable package (<https://visualstudio.microsoft.com/wp-content/uploads/2021/09/Visual-C-Runtime-2015-2022-License-1.docx>, SHA-256 `f1e3d56ceb2ad68aae0711b910375009e651ac5530fa0760f0dea6e81e54fae1`). The maintainer decided on 2026-10-25 to name the components and summarise the terms without reproducing them.

### What this does not cover

- The toolchain is derived from the release record and the nightly manifests, not read from the binary: the first time the inventory meets `rg.exe` is `checkCompiledRust` in the installer build, which fails (and names the commits that the binary carries) when the guess is wrong. The same holds for the Rust crates and the in-tree parts: they come from manifests, so a crate that the build links but that the rules above miss would be missing here, and `/rust/deps/<crate>-<version>/` paths in the binary would show it. The Microsoft terms are summarised, not reproduced, and what they mean for DatGold as a redistributor is a legal question that `THIRD-PARTY-NOTICES.md` states and does not answer.
- The list comes from the sources of the release. `rg.exe` was not opened when it was derived; what the installer build checks against it is the PCRE2 version string and what `rg --pcre2-version` prints, nothing about the crates. A crate that the build links but that the rules above miss would be missing here.
- These are inventories kept by the maintainers, not legal advice.

### Deriving it again for a new ripgrep release

1. Change the pin in `stage-ripgrep.ps1` (version, URL, SHA-256). Staging and `tests/verify-notices.mjs` fail until the inventory belongs to it.
2. Repeat steps 1 to 4 above for the new tag, and step 5 for the toolchain of its release run (the toolchain is the first thing that changes; a new Rust brings new crates and new in-tree notices: read `REUSE.toml`, `license-metadata.json` and `library/Cargo.lock` again), rewrite `ripgrep/` (texts and `MANIFEST.json`), and update the rows in `THIRD-PARTY-NOTICES.md` and `DATGOLD-HUB/THIRD-PARTY-NOTICES.txt` and the paths of `guest-lifecycle.ps1`. `node DATGOLD-HUB/tests/verify-notices.mjs` names what is left. The scripts used on 2026-10-25 are not part of the repository.
