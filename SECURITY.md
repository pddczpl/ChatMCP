# DatGold Security Policy

This policy describes the current single-owner, local-first Windows product. It does not claim a security audit, fully isolated host command execution, or live-browser acceptance of every website revision.

## Reporting a vulnerability

Use GitHub's private **Report a vulnerability / Security Advisory** option for this repository if it is available. Never post API keys, tokens, private keys, exploit payloads containing secrets, or personal data in public issues. If a private reporting channel is not available, open a minimal public [issue](https://github.com/pddczpl/ChatMCP/issues) asking the maintainer to arrange a private disclosure channel. Do not disclose the vulnerability details publicly before that channel is established.

## Supported deployment boundary

DatGold is designed for a single local Windows account with a Hub listening on **127.0.0.1:3007**. The desktop client and the browser dashboard communicate with the loopback Hub. Public port binding, reverse-proxy publication, cloud-hosted Cloud Harness infrastructure, public multi-tenant use, and mandatory cloud accounts are not supported deployment modes.

Every `/api/*` and `/auth/*` request to the local HTTP interface must carry a per-launch secret as `Authorization: Bearer`. The Hub makes a new secret at every start, keeps it out of URLs, command lines and the environment of child processes, and publishes it in `run/hub-session.json` inside its data folder, a folder whose access list grants only the owner's Windows account (the Hub does not start when that list cannot be set). Host, Origin and CSRF checks remain on top of it. **The secret protects against other Windows accounts, sandboxed processes that cannot read the owner's files, and web pages in the browser. It does not protect against malware or any other program running as the same Windows user, which can read the same file; loopback binding is not protection against such a program either.** Open exceptions to the first sentence: the Companion's two read-only status routes (`/api/extension-state` and `/api/instructions`) answer any request whose `Origin` header looks like a browser-extension origin, without the secret, so a local program can send that header and read the Hub version and the workspace path; and the Companion's pairing routes use a pairing code and their own token instead of the Hub secret. The file with the secret outlives a crash, so every client that reads it (the desktop app, the Node launcher and the PowerShell helper scripts `Stop-ChatMcpHub.ps1`, `Run-StudioSmoke.ps1` and `Test-Gateway-ViaHub.ps1`) presents the secret only to the process that listens on the port and is the one the file names, and sends nothing otherwise. Browser Companion pairing grants separately authenticated access for the user's own ChatGPT tab; it is not a public remote-control interface. [THREAT-MODEL.md](docs/THREAT-MODEL.md) lists these and the other residual risks of the credential, the Companion filter and the Read Only classifier.

## Permissions and execution isolation

- **Read Only:** inspect without approving file, shell, or Git mutations. Shell commands run in this mode only when the command classifier (`lib/command-analysis.mjs`, `lib/read-programs.mjs`) positively recognises them as read-only: a program is "read" only if **every** option is on that program's allowlist (exact long names, short clusters split letter by letter, `--opt=value` split first), and `sed` only for scripts that a strict grammar accepts (addresses plus `p`, `d`, `q`, `=` and `s///` with `g`, `p`, `i`, count flags) or under GNU `sed --sandbox`. Anything it does not recognise, such as `sed` `e`/`r`/`w` commands, `sort -o`, `uniq IN OUT`, `file -C`, `rg --pre`, `find -fprint`, `tree -o`, `less +cmd`, or a wildcard that could expand into an option, is treated as an unreviewed command and is refused. The classifier reads command text and is not a sandbox; `tests/fixtures/readonly-bypass-corpus.json` is the regression corpus.
- **Review:** ask the owner to approve potentially mutating or risky operations.
- **Autonomous:** allow only operations permitted by the selected policy and the PermissionGate.
- **Full Access:** requires explicit owner activation (typing `FULL ACCESS`). Everyday operations execute using the signed-in Windows account's effective permissions without per-call approval. This is not OS privilege elevation, nor a promise that host commands are harmless. Operations that cannot be taken back are **not** covered: anything classified `dangerous` (file/data deletion, history rewrites, `git push`, destructive `gh`, `npm publish`, `docker push`, `kubectl delete`, `terraform destroy`, cloud delete commands) and the tools `github_pr_merge` and `github_release_create` still produce an approval request in every mode, and Read Only still refuses them outright. A context with nobody to answer (a coding-orchestrator worker, or an agent that a model spawned while the owner runs Autonomous or Full Access) refuses such an operation immediately instead of waiting for the approval timeout. Model-spawned agents are also capped (default depth 2, 16 descendants per conversation).

Repository text, instructions in third-party skills, search results, agent replies, and tool outputs are untrusted inputs and may contain prompt injection. Path normalization, protected paths, permission checks, review tokens, checkpoints, and rollback guards reduce risk but do not make arbitrary shell commands safe. Git worktrees isolate branch checkouts, **not** host processes or filesystem permissions. Host command results must not be described as Windows Sandbox or independent attestation. Where supported, Windows Sandbox execution and sealed verification receipts have their own provenance requirements; experimental support does not prove every test runner is isolated or independently certified.

An interrupted or timed-out mutation can have uncertain effects. DatGold must preserve evidence and require inspection instead of blindly repeating file writes, Git operations, shell commands, or browser submissions.

## Credentials, providers, and diagnostics

Configured model API requests may transmit task instructions, selected source excerpts, tool definitions and output, images/attachments, and conversation context to the selected provider or custom gateway. **Local-first does not mean offline.** Users are responsible for selecting and trusting remote endpoints, verifying allowed sharing, and checking provider retention and charging terms. Ollama or LM Studio can operate locally when installed and configured separately.

Where stored, model credentials and custom gateway HTTP header values use the local Windows DPAPI-based secret protection mechanisms. Protected custom headers are bound to the exact configured provider origin, are never returned as plaintext in public state or diagnostic exports, and are cleared when switching to another origin. Environment-variable header references are resolved locally at request time; missing values fail rather than issuing a malformed request. Environment-sourced and session-only credentials have separate lifetimes. Switching credential destinations must not silently forward existing keys to an unrelated origin. Avoid entering sensitive content into model prompts or untrusted source repositories. Diagnostic exports and errors should redact known secrets, but redaction is defense in depth and not a guarantee against every accidental disclosure; inspect logs before sharing them.

Skills Hub downloads pinned repository assets and verifies content hashes; importing a skill is not permission to execute bundled scripts automatically. Upstream licensing and integrity must be reviewed independently.

## Browser Companion and desktop lifecycle

The separately installed Chrome/Edge Manifest V3 Companion pairs with the loopback Hub using a user-approved process. Its ChatGPT Web transport is constrained to supported text-based interaction and transport-specific safety checks. Everything sent through it goes into the owner's ChatGPT chat. Before the Hub hands a message to the Companion it replaces text shaped like a credential, withholds tool results that name protected files, and can hold each tool result for the owner's approval (off by default). These controls are pattern-based and best effort: they do not catch a secret without a recognisable shape or anything that is confidential only for a client ([ChatGPT Web Companion privacy](docs/COMPANION-PRIVACY.md)). Pairing does not grant API quota. Browser verification on scripted pages is not equivalent to a signed-in user's live ChatGPT session. If a send outcome is uncertain, recovery must not duplicate submissions.

The native desktop enforces single-instance activation, Hub identity/version checks, and ownership-sensitive lifecycle operations. Closing the GUI preserves the running Hub; use an explicit shutdown to stop it. The installer checks owned payloads, prevents unsafe active-task upgrades, stages changes, and retains rollback markers when completion is uncertain. These controls do not provide power-loss atomicity for an entire directory or defend against an adversarial process with the same Windows privileges.

## Update notice and download

DatGold can tell you that a newer release exists and, when you click **Download**, fetch its installer. The look is the one request the Hub makes with no task and no button of yours behind it (the model requests of a task you started and the list of models, fetched only when you press its button, are the others), and the Hub makes it **only after you have said yes** to a question the app asks once: until you answer, the Hub asks nothing. **Check now** in Settings → Updates is your own act and works whether you said yes, no or nothing. When it looks, the Hub sends a GET to `https://github.com/pddczpl/ChatMCP/releases/latest/download/RELEASE-MANIFEST.json`, which GitHub answers with two redirects (github.com, then release-assets.githubusercontent.com) to the manifest of the newest stable release, and then a GET to the signature of that release, `https://github.com/pddczpl/ChatMCP/releases/download/v<version>/RELEASE-MANIFEST.json.sig`, an address the Hub builds from the version it read in the manifest (GitHub says that there is no such file when the release has no signature; how it answers for a signature file that exists was not read, because none exists yet, and the Hub follows the same redirect rules as for the manifest). The headers are only `Accept` and `User-Agent: DatGold/<version>`: no cookie, no login, no body. The Hub follows at most 3 redirects, only to https on github.com, release-assets.githubusercontent.com or objects.githubusercontent.com, reads at most 64 KiB in 10 seconds (a signature file: at most 4 KiB, in the same time) and treats the answer as data: a release version x.y.z, never a pre-release. GitHub sees your network address and that a DatGold of that version runs. The first request comes about 30 seconds after the Hub starts, then about every 12 hours (an hour after a failure), never within 15 minutes of the last attempt (the attempt is noted before the request goes out, so a Hub that restarts in a loop still asks once per 15 minutes; where the note cannot be saved, the Hub does not look on its own), and a manual check is answered with a request at most once a minute. Your **No** counts from the moment the Hub receives it: a timer that fires while its file is being written asks nothing.

**Only a release whose manifest has a valid signature is offered for download.** The signature is ECDSA over P-256 with SHA-256, made over the exact bytes of `RELEASE-MANIFEST.json` as published (the Hub checks the exact bytes it received and never re-serializes them; it reads the version in the manifest first, to know which signature to ask for, but a download takes nothing from the manifest until the signature has checked), and it is checked against the public keys listed in `CHATMCP-HUB/lib/release-keys.json`, a file that ships in the installation and has room for four keys, so that the next key can ship before it is needed. A release with no signature file, or with a signature that does not check or was made with a key the Hub does not know, is announced with the reason and without a Download button. The file ships with a placeholder instead of a key until the project's owner has made the release key, and a placeholder trusts nothing: until then no release can be downloaded through the app. The private key is not part of this repository: `scripts/new-release-key.mjs` refuses to write it inside any Git working tree and never prints it, `scripts/sign-release.mjs` makes the signature by hand, and the release gate (`scripts/verify-release-source.py`) refuses to publish a release while the key file holds a placeholder or a test key.

**A download starts only from your click on Download**: never from a timer, at start-up, after a check or after you said yes to automatic checks, and it is allowed while tasks run. The click carries a version and nothing else. The Hub fetches the manifest of that release again by its tag, checks its signature again, and takes the name, size and SHA-256 of the installer from it and from nothing else; the address of the installer is built from the version and that name, which must be a plain `.exe` file name. The installer is streamed to a `.part` file under `<data folder>/updates/<version>/` and is never held in memory; it is counted and hashed as it arrives and kept only if its size and SHA-256 are the signed manifest's, otherwise it is deleted. The Hub needs twice the installer's size free on the disk, takes at most 2 GiB, follows the same redirect rules and gives up after 60 seconds without a byte. **Nothing is installed or run in this step**: the installer waits in its folder beside the signed manifest and its signature, it is not opened or moved once it is there, and "Downloaded and checked" is the Hub's statement about the bytes at the time they arrived. The step that will run it must hash it again and check the kept signature again before it does.

What this does not do: the signature shows that a manifest was made with the owner's release key; it does not make the installer Authenticode-signed, which it is not, so Windows SmartScreen can still warn when you run it. Whoever holds the private key can sign anything, and a key that is lost or leaked is replaced only by a new installer that carries a new key list. A program that runs as you can read the Hub's secret, press Download, and change the key file or the downloaded installer (see the first section). The feed address is fixed in the code: no setting, route or page can change it (a test can point it at a loopback address, and only at one). A proxy is not used. [THREAT-MODEL.md](docs/THREAT-MODEL.md) (Surface 8) lists the limits.

## Distribution and historic risk

Validate downloaded installers and Companion archives against the release SHA-256 files and release manifest. Verify Authenticode independently when a publisher signature is present. An unsigned installer must be described as unsigned; checksum verification only checks byte integrity relative to the published hash. Signing must precede final checksum calculation. The signature on the release manifest (see the Update notice section) is separate from Authenticode and replaces neither it nor the comparison of checksums.

Older repository history may still contain retired Cloud Harness configuration or credentials. Removing files from the latest branch does **not** erase Git history or revoke a leaked secret. Rotate any potentially exposed credentials and separately decommission old servers, tokens, and deployment resources. Do not treat passing CI, successful packaging, or release checksums as a penetration test.
